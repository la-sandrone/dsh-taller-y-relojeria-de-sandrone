补一条**反方向**的实证：同一个 400 不只在「PTC 基线 → 退化 native」时出现，**native 基线 → 切到 PTC** 时同样必挂。

环境：DSH `v0.2.2-rc.1`（比本 issue 的 rc.3 更晚），官方账户模型。

会话实况（从 `request/header` 逐条解出）：

- `seq 11`：model `deepseek-flash`，tools = **132 个原生工具**（ask_user_question / bash / company_scan / deepread / edit …）
- `seq 2728`：model `deepseek-v4.1-flash`，tools = **1 个 `run_code`**
- `assistant/attempt` `seq 2716`（turn 81 / step 1）：`INVALID_REQUEST 400`，`request_id: 158191bb-3e30-46e0-ae84-d19941636ce7`

指向 `packages/llm/llm/src/content.ts` 的 `toolDeclarations()` / `projectToolUpdates()`：

1. `declarations` 以**历史基线**为底（这里是 132 个原生工具）
2. 后来才出现的 `run_code` 被写入时标 `deferLoading: true`
3. `addition-only` 分支把**当前不活跃**的名字全删 ⇒ 只剩那个迟到且延期的 `run_code`
4. ⇒ 整份 tools 全延期 ⇒ 服务端按不变量拒绝

所以修复点应该比「让 liangshen 不要退化」更靠内一层：**投影结束后若 `declarations` 全为 `deferLoading: true`，至少要保留一个 immediate 声明**（`BotHarness/DeepSeekBot#3137` 的期望也是这句）。两个方向（132→1 / 1→70）在这一处是同一个漏洞。

两条附带判据：

- 该字段只有官方 provider 适配器会发（`llm-deepseek/src/serialize.ts:165`）；自定义 `openai-completions` 端点的 `toolUpdate` 是 `undefined`，`content.ts:433-434` 会**剥掉**延期标记 ⇒ 同一会话换自定义端点即可继续。可作为「不是会话坏了」的旁证。
- 影响面：**工具面中途变过形态的会话全部**如此，不是个别 preset；我们这种自建 profile（5 个 preset / 10 个 MCP、会话跨 81 轮 337 步）命中率不低。

建议：若下次发版只修 liangshen 的 `presentAs` 退化，这类会话仍会 400；要么在投影层兜住，要么给一条「该会话基线与当前工具面不相交」的**显式告警**（现在完全静默）。
