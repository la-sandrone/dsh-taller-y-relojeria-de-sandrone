## 〇、一句话结论

**两件事同时成立：**

1. ✅ **启动器的主路径是派生的** —— 改 `DSH_VERSION` 一个文件就能起 0.2.0
2. ⚠️ **但不是"只靠它"** —— 周边 7 处硬编码，其中 **1 处会让一道安全门静默失效**

第 1 条决定了"能不能切"，第 2 条决定了"切了安全不安全"。

## 一、✅ 派生的那部分（干净，无需改）

通路是一条链，每一环都从 `DSH_VERSION` 算出来：

```bash
start-web.sh:64    readonly HOME_PREFIX="dsh-domus"                # 前缀是常量，不是版本
start-web.sh:99      DSH_VERSION="$TRY_VERSION"                    # --try 时由参数覆盖
start-web.sh:109   HOME_NAME="${HOME_PREFIX}-${DSH_VERSION#v}"     # ← 派生：去掉前导 v 拼前缀
start-web.sh:111   readonly DSH_HOME_DIR="$SCRIPT_DIR/$HOME_NAME"  # ← 派生
start-web.sh:400   export DSH_VERSION
start-web.sh:401   export DSH_HOME="$DSH_HOME_DIR"                 # ← 派生
```

**关键更正**：`DSH_VERSION` 文件自己的头注释写着「`start-web.sh` 里的 `export DSH_HOME`
是**独立硬编码**的」——**那句话已经过时了**，代码早已改成派生（见上面第 401 行）。
这条注释把"过去的状态"当成"现在的状态"讲，会误导后来者（= 下方 #7）。

同样干净的消费方：

| 文件 | 为什么干净 |
|---|---|
| `bin/dsh` | `DSH_HOME`/`DSH_VERSION` 用 `:=` **原样继承调用方**，缺省才回落读 `DSH_VERSION` 文件（`bin/dsh:34-36`）。里面的 `dsh-domus-0.1.5-rc.2` 全在**注释叙述一个已修的历史 bug**，不是活逻辑 |
| `tools/check-profile-links.py` | `--home` 缺省 `None` ⟹ 按 `DSH_VERSION` 派生（L70-75、L264） |
| `tools/dsh-force-h1.mjs` | 先读 `DSH_VERSION` 拼路径，再枚举 `原始代码研究/*` 兜底（L46-49） |
| `bin/dsh-dryrun` | 刻意指向固定的 `dsh-domus-dryrun`，**不跟版本走**——它的语义就是"与现役隔离的副本" |

## 三、最要紧的 #1：门本身是魔数驱动的

```bash
# start-web.sh:356-369
# 为什么需要：版本与 home 名是两个独立真相源。2026-09-26 那次翻车
# （插件禁用风暴 + "对话全空"）就是只改了版本、home 没跟上，于是 0.1.7
# 基座去加载 0.1.5 的 profile。这里把那条教训变成一道启动门。
if grep -q '0.1.7 迁移物' "$PROFILE_YML"; then PROFILE_HAS_017=1; else PROFILE_HAS_017=0; fi
case "$DSH_VERSION" in
  v0.1.7-rc.2)
    [ "$PROFILE_HAS_017" = 1 ] || die "基座 $DSH_VERSION 需要 0.1.7 迁移物，但 $HOME_NAME 的 profile 里没有。
    这正是 2026-09-26 翻车的组合（新基座 + 旧 home 配置）—— 拒绝启动。" ;;
esac
```

**问题不在"漏改一个数字"，而在设计形状**：

- 门按**版本字面量**分支 ⟹ **每加一个版本，都得记得补一个 `case`**；忘一次，就**静默裸奔一次**
- 而它防的恰恰是**最危险的那类操作：换大版本**。**你越需要它，它越不在。**
- 危害形态是**静默**：不匹配 ⟹ 不报错 ⟹ 照常启动 ⟹ 出问题时你完全想不到这里少了道门

### 正确的形状：属性驱动

**让基座自己声明它要求 profile 具备什么**，`start-web.sh` 读声明来判——**加版本 = 加数据，不是改逻辑**：

```bash
# 检出树里放一份声明（eg. 原始代码研究/$DSH_VERSION/REQUIRES_PROFILE_MARKER）
# 内容就是它要求 home 的 profile 必须含的标记
REQ_FILE="$SCRIPT_DIR/原始代码研究/$DSH_VERSION/REQUIRES_PROFILE_MARKER"
if [ -f "$REQ_FILE" ]; then
  REQ="$(cat "$REQ_FILE")"
  grep -qF "$REQ" "$PROFILE_YML" || die "基座 $DSH_VERSION 要求 profile 含「$REQ」，但 $HOME_NAME 里没有——拒绝启动。"
fi
```

这样：**新版本只需在新检出树里放一个文件**；**没有声明 = 没有要求**（显式、可查、不靠记忆）。
配套纪律：**给新版本建 home 时，必须同时写这份声明。**

## 六、python 重写期间的新增发现（2026-10-08 实测）

这一节是搬家的副产物：把 bash 逐条翻成 python 时，每一处的「它到底在判什么」
都必须想清楚，于是原本隐藏的失效被照出来了。

### 🔴 新 #8 · `start-web.sh:375-384` 的路径自检是**结构性死检查**

它从未拦下过任何东西。原式：

    LEAK="$(grep -rlE '/deepseek-harness/dsh-domus(-[0-9]|/)' "$PROFILE_YML" "$PATCH" \
            | grep -v "/$HOME_NAME/" || true)"

`grep -rl` 给出的是**文件名**；而两个候选文件**都在当前 home 内**，其绝对路径必然
含 `/<HOME_NAME>/`，于是被 `grep -v` 无条件滤掉 ⇒ **LEAK 恒为空**。

实测复刻（绝对路径，与真实启动器一致）：`LEAK=[]`。

> 我第一次用**相对路径**测，得出「没被滤掉、检查是好的」的**相反**结论 ——
> 判据本身的构造错了会给出反向答案。这是「先复刻现场再下结论」的一个正例。

**修法有陷阱**：不能改成「文件内容提到了某个 home 名就算泄漏」。实测本 home 的配置里
提到 `dsh-domus-0.1.7-rc.2` / `dsh-domus-0.1.5-rc.2` **各一次**，但那是**注释里的散文**
（「来源：现役 dsh-domus-0.1.5-rc.2/…」），不是路径 —— 按名字判会把**现役实例挡在门外**。
正确判据：**内容里出现的【绝对路径】，其 home 段不等于当前 home**。
实测该判据对现役 home 通过（出现的绝对路径只有当前 home 名）。

已在 python 版修好（`start-web.py: guard_path_leak`），并且**带行号**报出。

### 🟠 新 #9 · `bin/dsh:36` 缺省 home 硬编码 `dsh-domus-0.1.7-rc.2`

0.2.0 上线后它就是一个**错的默认值**：裸终端里敲 `dsh` 会落到 0.1.7 的 home。
已在 `bin/dsh.py` 改成与启动器**同一个派生式**（`<前缀>-<版本去掉一个前导 v>`）——
**删掉魔法数字**，不是把它换成另一个版本号。

### 🟡 新 #10 · 运维守护「第一次启动之后再也不重启」⇒ 环境永久冻结

`dsh-ops-daemon.sh:25-27` 靠 `flock -n` 做幂等：新的守护发现有人持锁就 **`exit 0`**。
于是启动器每次启动都会拉起一个守护，而它**每次都立刻退出**（实测 10:29:38 那行
「已有实例在跑(flock)，本进程退出」）⇒ 真正在跑的那份**从第一次启动起就再没换过**，
它的进程环境（`PWD`/`DSH_HOME`/`DSH_VERSION`）冻结在那一刻。

实测（2026-10-08）：现役守护 **pid 602**（ppid=1）的环境仍是
`PWD=原始代码研究/v0.1.7-rc.2`、`DSH_HOME=dsh-domus-0.1.7-rc.2`、`DSH_VERSION=v0.1.7-rc.2`。
**正确读出的启动时刻：2026-10-04 13:12**（那次开机后 47 秒），至今 **3.9 天 = 当前 uptime 的全部**
—— 它完整跨过了 0.1.7 → 0.2.0 的切换。

> ⚠️ **我第一次把这条标成 🔴、并说成「boot 时代」，严重度判错了。** 两个原因：
> ① 我用 `awk '{print $4}'` 读 `/proc/<pid>/stat` 当 starttime —— 第 2 字段 `(comm)`
>    含空格与括号，naive 切分把字段位置整体带偏（**这正是我在 `start-web.py:proc_starttime`
>    里特意注释过的坑，然后我用 bash 一行流自己踩了**）。正确读法是
>    `sed 's/.*) //' /proc/<pid>/stat | awk '{print $20}'`。
> ② **「环境冻结」听起来骇人，但实测无害**：通读守护全文（97 行）并 grep 它调用的
>    `tools/dsh-trace-ingest.py` 与 `_scratch/watch_status.py` —— **三处都不读
>    `DSH_HOME`/`DSH_VERSION`/`DSH_TRACE_LOG`**，`REPO` 是第 15 行的硬编码常量。
>    所以那个过时环境是**惰性的**，不影响它干什么。

⟹ 降级为 🟡：**潜在陷阱，不是现患**。一个带着错误身份、可能永远不重启的常驻进程，
读起来像在管 0.1.7，实际谁也没管 —— 这类「看起来在监视」的守夜人值得警惕，
但它今天没有造成任何错误行为。

### 🟠 新 #11 · per-instance 的取证日志**只有写侧，没有读侧消费者**

- **写侧**：`DSH_TRACE_LOG`（现役启动器 = `_scratch/trace-9007/fetch-trace.log`；
  python 版 = `<记录目录>/fetch-trace.log`）
- **读侧**：守护读的是 **`_scratch/fetch-trace.log`**（`dsh-ops-daemon.sh:16` 的固定路径）
- 而 `dsh-fetch-trace.mjs:30` 是 `process.env.DSH_TRACE_LOG ?? '<默认 _scratch/fetch-trace.log>'`

⇒ 两个文件**都在长**（实测 10:30）：`_scratch/fetch-trace.log` **18.6 MB / 41106 行**；
`_scratch/trace-9007/fetch-trace.log` 1.17 MB / 2207 行。
默认那份收的是**没有 `DSH_TRACE_LOG` 的进程**（典型：由 harness 另起环境的 node 类 MCP 服务）
的流量；per-port 那份收的是 host 侧。

**所以 #10 的影响是有限的**（守护不读 home 下的东西，只读那个固定路径），
但 #11 本身是真的，而且比「日志没人读」更严重一层：

> **守护看的是「没有实例身份的进程」的流量，看不见 host 自己的流量。**
> 而 host 的流量（LLM 请求、TRANSPORT 故障）恰恰是**症状哨兵最该看的东西**。
> ⇒ 从 per-port 重定向（`DSH_TRACE_LOG`）被引入的那天起，**症状哨兵就在看一份片面的信号**。
> 两个文件都在长（18.6 MB vs 1.17 MB）就是这个的指纹。

**同一形状还有第二处**（同一次通读发现）：守护第 36 / 42 行读
`"$REPO/tools/h1-mode"`（**无端口后缀**），而启动器设的是
`DSH_H1_MODE_FILE=tools/h1-mode-$PORT`。
实测：`tools/h1-mode` 是 **2026-09-25** 的 3 字节旧文件；`tools/h1-mode-9007` **根本不存在**。
⇒ 守护报告的「臂: h1-mode=…」读的是一个**早已不再被更新的遗留文件**。

另有一件**无上限增长**的事：`_scratch/fetch-trace.log` **18.6 MB 且无任何轮转**，
而它同时是守护的**唯一输入** —— 想给它加 TTL，得连**摄取游标**一起设计，
不能直接删（游标是文件内的行号/偏移，实测日志里的「游标 41097 → 41100」就是它）。

**共同形状**：**同一件事实有两个位置，而其中一个已经不动了** ——
per-instance 路径 vs 遗留固定路径、0.1.7 环境 vs 0.2.0 现况。
与本文 §一至§三 那 7 条是**同一种腐坏**。

## 七、「按需挂载」的定案（2026-10-08）

用户原话：

> 本来就是调试工具，正经人谁每天日常上网挂 F12 的？不都是出了问题或者要干嘛才挂吗？

这个类比不只是打比方 —— 它把设计一条条定死了：

| F12 的性质 | 对应到运维守护 |
|-----------|----------------|
| 按需挂载，不随浏览器自动开 | 手动调用，启动器不再拉起（门 7 取消） |
| **挂在具体目标上**（某个标签页） | 挂在**具体实例**上（`--log <记录目录>/fetch-trace.log`） |
| 生命周期跟随被观测对象 | 实例没了就该重挂 |
| 晚开只丢「刚才那段」，证据在服务端 | 晚挂只丢**实时报警**，行仍在 MariaDB |

**代价说准**（两条实测依据）：

| 事实 | 依据 | 后果 |
|------|------|------|
| 游标存在 MariaDB | `tools/dsh-trace-ingest.py:5` —— `test_db.dsh_transport_ingest.lines_done`（行号），可断点续传、可重复运行不重插。实测**按文件**记：换一个日志时游标从 **0** 起，而不是接着旧日志的 41105 | **数据不会丢**，晚挂能补全 |
| 哨兵基线是挂载那一刻的行数 | `dsh-ops-daemon.sh` 里 `BASE=$(wc -l < "$LOG")`，之后只扫增量 | **实时报警会漏**（错过的只能去查 MariaDB） |

⟹ **丢的是「有人主动喊你」，不是「证据」。**

**为什么这条比「让守护跟着版本走」更好**：它同时解掉「谁拥有它」——
手动起的进程带的是**你当时**的环境，于是「环境冻结」这个陷阱**从根上不存在**。
而且它是本项目已有那条原则的正面运用（cutover 那轮写下的）：

> 一个进程，如果它的职责是停止 DSH，那就绝不能从 DSH 里面被拉起

同一说法的另一面：**一个进程的生命周期与环境，不该由「第一次谁碰巧拉起了它」决定。**

**补上「缺席可见」**：改成手动之后，「没人起它」成为常态 ⇒
`start-web.py --status` 增加一段报告它**在不在**、**带着什么环境**、
**与当前实例是否一致**（后者正是「环境冻结」的显形），以及一条**现成的挂载命令**
（带好当前实例的日志路径，免手打）。
理由就是那条老规矩：**它不在场，就让它显形 —— 不许变成静默没人记。**

**实测记录（2026-10-08）**：
- 停 pid 602（它带着 v0.1.7 环境跑了 3.9 天）—— 停掉后那个 `sleep 20` 成了孤儿，
  活到自然结束。**这正是新版加 `sleep & wait` + `trap` 的原因。**
- 新工具实挂 30 秒：摄取 2424 行（游标 0 → 2432，8 行不可解析）；
  SIGTERM 后打印「收到停止信号，已卸载」；**无 sleep 孤儿**；flock 锁正常释放；
  `--help` / 未知参数 / 日志不存在 三条路径都返回 2。

**尚未解决**：`_scratch/fetch-trace.log` 那个 18.6 MB 的**遗留共享 sink** 仍在无上限增长，
给它加 TTL 要连游标一起设计（游标按文件、记行号）。
