# 公开仓工具的可移植化（根目录解耦 + 发布件改写）

**日期**：2026-10-11
**起因**：公开仓那几个工具硬编码了 `$HARNESS` —— 对陌生人是"参考实现"而不是即用件。用户裁定走 **(ii) 先解耦再发**。

## 一、根目录解耦：沿用**既有**约定，不新造

`DSH_HARNESS_DIR` **本来就存在**（`start-web.py` 给子进程注入它；`dsh-force-h1.mjs` 早就读它）⇒ 解耦只是把这个约定补齐：

**解析顺序**：`DSH_HARNESS_DIR` → **由脚本自身位置推导**（`tools/` 的上一级）→ **推不出就报错**（不猜一个可能错的根）。

| 文件 | 原状 | 现况 |
|---|---|---|
| `tools/repair-profile-links.py` | `HARNESS = Path("$HARNESS")` | `_resolve_harness()`：env → `parents[1]`（并要求同级有 `tools/` + `start-web.py` 才认）→ 否则 `sys.exit` 报错 |
| `tools/check-profile-links.py` | `HARNESS_DEFAULT = Path("~/…")` | `_default_harness()`：env → 推导 → 退回 CWD（`--harness` 显式覆盖仍最优先） |
| `tools/dsh-force-h1.mjs` | `process.env.DSH_HARNESS_DIR ?? '$HARNESS'` | `process.env.DSH_HARNESS_DIR ?? fileURLToPath(new URL('..', import.meta.url))`（去掉尾斜杠） |

**其余 5 个已发布文件本来就可移植**（`start-web.py` / `dsh_config.py` / `dsh_instance_env.py` / `dsh-ui-patches.py` / `check_patch_layers.py`：0 处硬编码）—— 它们从 `__file__` 派生路径。

✅ **实测**：两个语言推导出的根都是 `$HARNESS` ⇒ **本地行为零变化**。

## 二、草稿区名：交给导出管线改写（自用版 ≠ 发布版）

工作区自己的草稿目录叫 `草稿纸与垃圾桶/`，这在公开仓里是个无法解释的名字。处理方式是**确定性转换**而不是人手改两份：

```python
# tools/export-dsh-collection.py
PUBLIC_REWRITES = [(re.compile(r'草稿纸与垃圾桶'), '.dsh-scratch')]
PUBLIC_REWRITE_SCOPE = ('start-web.py', 'start-web.sh')   # 另加 tools/ 前缀
```

- 实测命中 4 处：`start-web.py` ×2、`tools/dsh-force-h1.mjs` ×1、`tools/repair-profile-links.py` ×1
- ⚠️ **刻意不作用于 `notes/`** —— 那些笔记记录的正是工作区自己的布局，改名会让它们**失真**（"说了 A 实际是 B"）。改写只对"代码里当路径用"的地方成立。
