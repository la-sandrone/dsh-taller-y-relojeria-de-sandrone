# 启动器绑定地址与远程访问「砖」

文件名: 用户笔记/部署/启动器绑定地址与远程访问砖.md
摘要: 2026-10-20 远程访问的「局域网访问」开关把 webserver 绑到局域网 IP，回环失联 → 配对面板够不着 → 锁死。修法：启动器永远注入 `--host 127.0.0.1`。
依赖: `start-web.py`、`dsh-domus-*/profiles/web/cordis.patch.yml`、`@linxin666/dsh-remote-web-ui`

---

## 一句话

`remote-web-ui` 的「局域网访问」开关会把 `webserver.host` 写成局域网 IP，
**`127.0.0.1` 随即不再监听**；而它的配对面板**只在回环可用** ⇒ 一绑就锁死。

## 现场（2026-10-20，用户实际踩到）

开启「局域网访问」后：

```
访问 127.0.0.1:9007    → 连接被拒（没人监听）
访问 <lan-ip>          → 非回环来源 →「需要设备配对」拦截页
想配对                → 面板只在回环可用 → 够不着
```

**回环死了，而唯一的救命入口在回环。** 最后靠注释掉受管块救回。

## 机制：为什么这是必然，不是操作失误

1. 插件的「局域网访问」往 profile 写受管块：`host: '<lan-ip>'`
2. **DSH 0.2.1-rc.2 拒绝通配绑定** —— `0.0.0.0`/`::`/`::0`/`0000::` 等全部视为非法
   （`packages/host/webserver/tests/webserver.spec.ts:240`；
   文档 `apps/cli/reference/README.zh.md:111`）
3. 只能绑一个具体地址 ⇒ 绑了局域网就丢掉回环
4. `webserver` 只有**一次** `listen(port, host)`，且 `config.host: string` 是单值
   （`packages/host/webserver/src/index.ts:517`）⇒ **不支持多 IP**，
   文档也写明「`hostname -i` 可能列出多个，请只传一个」

**结论：在 0.2.1-rc.2 上，「局域网直连」与「配对面板可达」不可兼得。
`lanBind` 这个功能实际不可用。** 不是配置问题，是版本约束。

## 修法（两处，已落地）

### ① 启动器永远注入回环 —— 免疫，而不是防

`start-web.py`：

| 改动 | 位置 |
|---|---|
| `BIND_HOST = "127.0.0.1"` 常量 | 常量区（`BASH`/`SS` 旁边） |
| `args` 加 `--host BIND_HOST` | `spawn_host()` |
| `detect_lan_bind()` 启动前体检 | `spawn_host()` 上方，函数内置调用 |

依据：**`--host` 旗标优先级高于受管块**（`apps/cli/reference/README.zh.md:111`
「显式 `--host`/`--port` 旗标仍然优先」）⇒ 注入即永久免疫，
不管插件往 profile 里写什么。

### ② profile 配置

`dsh-domus-0.2.1-rc.2/profiles/web/cordis.patch.yml`：

```yaml
- id: web-ui-remote-web-ui
  name: "@linxin666/dsh-remote-web-ui"
  config:
    autoTunnel: true
    lanBind: false
```

⚠️ **`lanBind` 必须保持 `false`。**

**插件会在启动时自动重写受管块**：`lanBind:false` → 写 `127.0.0.1`；
`lanBind:true` → 写局域网 IP（实测：改完配置后插件立刻把块重写成了 `127.0.0.1`）。
所以**不要手动编辑受管块**（下次启动就被覆盖）；要改绑定地址，改 `BIND_HOST`。

## 救砖接口（记住这一条）

```bash
dsh web --host 127.0.0.1 --port 9007
```

`--host` 覆盖受管块 → 回环恢复 → 进面板把开关关掉。
**不用改配置文件、不用翻界面。** 这就是那个「隐藏的救砖按钮」，
文档里藏在「局域网绑定开关」那一条的括号里（「显式旗标仍然优先」）。

## ③ 关掉并排的第二个配对入口（bridge）

**症状**：侧栏底部有两个长得很像的入口，点错就扫不出网址。

| 图标 | 组件 | 插件 | 用途 |
|---|---|---|---|
| **听筒** | `PhoneIcon`（`RemoteEntry.tsx`） | `dsh-remote-web-ui` | 手机**浏览器**扫码进 Web GUI |
| **四个方块（QR）** | `QrIcon`（`PairEntry.tsx:134`） | `dsh-remote-bridge` | 原生 App 的协议 v1（配对码，非 URL） |

点错 QR 那个的后果：微信扫出来是一串字符（`4q2Z…`），**这是正常的**——它的二维码内容就是配对码，不是链接，而且 30 秒就过期。

**禁用**（2026-10-20 实测有效）：

```yaml
- id: web-ui-remote-bridge
  disabled: true
```

**关键结论**：`dsh-web-all` 聚合包用 `- insert:` 插入的子插件行，
**可以在 profile 的 `cordis.patch.yml` 里用同 id + `disabled: true` 覆盖掉。**
不需要改聚合包（它的 patch 是 `scripts/aggregate.mjs` 自动生成的，改了会被覆盖）。

两条远程面互相独立，关掉 bridge 不影响 web-ui 扫码。

## ④ 手机端底部露一块（适配层的选择器对了半）

**症状**：手机上 composer 下面露出一条背景（壁纸渐变/纯色），像页面没铺满。

**根因**：插件的移动适配层用**语义类名后缀**做选择器，而 0.2.1-rc.2 改掉了一部分类名。
实测 `apps/web/dist` 构建产物：

| 类名 | 存在 |
|---|---|
| `_bubble` / `_input` / `_scroll` | ✅ |
| `_frame_1hfzl_1` | ✅ |
| **`_centerCol`** | ❌ **0 处** |
| `_composer` / `_railFish` / `_newSession` / `_panelIcon` / `_scrollBody` | ❌ 0 处 |

于是 `[class*="_frame"]:has([class*="_centerCol"]){height:100dvh}` 这条**永远不匹配** →
frame 拿不到满屏高度 → 底部露底。

**workaround（已打，2026-10-23）**：

文件 `profiles/web/node_modules/@linxin666/dsh-remote-web-ui/lib/client.js` 第 4246 行：

```js
// 原：需要 :has(_centerCol) 才生效（永假）
"[class*=\"_frame\"]:has([class*=\"_centerCol\"]){width:100%;height:100dvh}",
// 改：无条件匹配唯一的 _frame_ 类
"[class^=\"_frame_\"]{width:100%;height:100dvh}",
```

- 备份：同目录 `client.js.bak-frameheight`（247546 字节，含 3 处 `_centerCol`）
- `[class^="_frame_"]` 安全：构建产物里 `_frame` 开头的类**只有** `_frame_1hfzl_1` 一个
- **插件更新会覆盖这次修改** —— 升级后若露底复发，重打这一行

**没修的**：`_composer`（键盘安全区内边距）、`_railFish`（44px 触控目标）、`_scrollBody`（字号）这几条仍然失效。
只影响手感，不影响能不能用。等作者按新类名更新适配层。

## 首次启动的「插件加载失败」是吓人的，不是坏的

重启后第一次打开 Web GUI，控制台会刷一片加载失败，**自动刷新一次就正常**。

判据：

- 刷新后正常 → **启动时序竞态**（客户端 bundle / manifest 尚未就绪），无害
- 刷新后仍然失败 → 那才是真故障，去看 `启动器配置和日志/运行记录/<时间>-PID<pid>/` 的日志

不要因为这一片红字去回滚配置。

## 判据（下次别再试）

- 远程访问**只走隧道**，不碰局域网绑定
- 想同 WiFi 加速直连？**做不到**（机制第 3、4 条），别试
- 看到 `lanBind: true` 就当事故处理
- 隧道方案本身是安全的：`autoTunnel` 不改绑定，只在外面套一层 Cloudflare
