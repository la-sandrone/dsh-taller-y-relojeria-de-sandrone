# Node 强制 IPv4（opencode.ai 卡顿的正解），以及代理为什么被否决

## 一、起点：症状与错误直觉

DeepSeek 官方（`api.deepseek.com`）与 OpenCode Go（`opencode.ai`，baseUrl
`https://opencode.ai/zen/go`，30 个模型共用这一个 host）并行使用，后者很卡。
第一直觉是「境外站，挂代理」——**实测否掉了**。

## 二、代理臂实测（否决依据）

代理入口：`127.0.0.1:8999`（WSL mirrored 网络，即 Windows 侧的 Clash 类软件；
配置里的 `DSH_RELAY_PROXY` 也指向它）。`ProxyAgent` 只吃 `http(s)://`，
所以用 `http://` 而非你 export 的 `socks5://`。

单请求 20 次对照（`curl --http1.1`，`opencode.ai/zen/go`）：

| 臂 | 成功 | 建连 | 复用后每请求 |
|---|---|---|---|
| 默认直连（IPv6 优先） | 19/20 | 0.4–0.8 s | — |
| IPv4 直连（`curl -4`） | **6/6** | 0.19–0.23 s | **0.28 s** |
| 代理 8999 | **10/20** | — | 0.33 → 7.4 s 抖 |

失败形态统一是：

```
curl: (35) TLS connect error: error:0A000126:SSL routines::unexpected eof while reading
```

且**不是 opencode 专项**：同一代理访问 `www.cloudflare.com/cdn-cgi/trace`
也 3 次挂 1 次。代理节点本身是活的（`google.com/generate_204` → 204，1.29 s）。
⇒ 是「代理到 Cloudflare」这一段的问题，换域名无用，换节点才有可能。

keep-alive 复用更直观：

```
IPv4 直连 · 单连接连发 6 次：1.00 0.88 0.28 0.29 0.28 0.28  (s)
代理      · 单连接连发 6 次：7.4  5.6  1.48 0.36 0.33 1.23  (s)
```

**结论：给这个 host 挂代理是负收益。**（2026-11-04 定；节点若换到对 CF 稳的
线路需重测，届时可分流的方案见文末「如果将来还要上代理」。）

## 三、正解：把 Node 钉在 IPv4

`opencode.ai` 的 DNS 返回 **AAAA 在前**（`2606:4700:78::90:0:140~143` 四条，
其后才是 `172.65.90.20~23`）。Node 的 `dns.lookup` 默认 verbatim 顺序 +
undici 的 `autoSelectFamily`（Happy Eyeballs）会去试 IPv6，而中移动到
Cloudflare 的 IPv6 路径是**建连黑洞**——不是「慢」，是超时。

### 三臂实测（undici 8.11.2，同一进程连发 4 次 `fetch`）

| Agent 配置 | 四次耗时 |
|---|---|
| 默认（`allowH2` 缺省 true） | 8394 ms → **`UND_ERR_CONNECT_TIMEOUT`@10490 ms** → 3736 → 1435 |
| `allowH2:false`（本补丁原样） | 4382 → 2877 → 284 → 277 |
| **`allowH2:false` + `connect:{family:4}`** | **879 → 1062 → 887 → 296** |

默认臂直接给出连接超时——这就是「很卡」的现场。

### 为什么是 `connect.family`，不是 `--dns-result-order`

`--dns-result-order=ipv4first`（或 `dns.setDefaultResultOrder`）**只改排序**，
Happy Eyeballs 依然会把 IPv6 也试一遍，黑洞照样吃掉 10 秒。
`connect: { family: 4 }` 让 `dns.lookup` **只取 A 记录**——AAAA 根本不被解析，
`autoSelectFamily` 无事可做。这是本轮唯一真正生效的开关。

## 四、改动（一处，2026-11-04）

`tools/dsh-force-h1.mjs`（我们自己的 preload，不在基座检出里，升级不丢）：

```js
const agent = new found.mod.Agent({ allowH2: false, connect: { family: 4 } })
```

- 与 `allowH2:false` **放在同一个 preload**：两者都是给运营商链路兜底的
  传输层策略，且都作用于 undici 全局 dispatcher——拆成两个 preload 只会互相覆盖。
- 文件**不改名**：`NODE_OPTIONS` 注入、`dsh_instance_env.py` 的 `_OWN_PRELOADS`、
  剥 preload 逻辑都认这个名字，改名要动四处。
- 取证日志新增 `ipv4Only: true` 字段；`event` 与 `applied` 保持原样
  （`tools/dsh-trace-ingest.py` 按这两个字段分组，不能动）。

### 为什么这个 preload 装的东西不会被上游冲掉

`@deepseek-ai/dsh-http-proxy` 的 `installProxyFromEnvironment()` 在
`runProfile()` 里、**插件挂载之前**调用；但它的 `installGlobalProxy()` 在
policy 为 `none`（没有标准代理变量）时**完全不碰 dispatcher**
（`install.ts:181-190`）。而启动器的门 4 正好把所有代理变量清空
（`start-web.py` 的 `guard_proxy()`）⇒ 我们的 dispatcher 活得下来。

**但这条依赖关系是脆的**：哪天有人启用 `HTTPS_PROXY`，上游就会覆盖 dispatcher，
**IPv4 与 H1 一起丢失**。启用代理时必须同时确认这件事。

## 五、验证方法（可复跑）

```bash
# 1) 语法
NODE_OPTIONS= node --check tools/dsh-force-h1.mjs

# 2) 生效 + 真的走 IPv4（抓 443 的 peer 地址，看是 172.65.90.x 还是 2606:4700::）
DSH_TRACE_LOG=/tmp/.dsh-tmp/trace.log \
NODE_OPTIONS="--import file://$PWD/tools/dsh-force-h1.mjs" \
node /tmp/.dsh-tmp/verify-ipv4.mjs
```

2026-11-04 实测输出：`arm: {"forced":true,"ipv4Only":true}`、
`established-443: 172.65.90.20:443`、`302@753ms 302@1113ms 302@278ms`。

## 六、生效与回退

- **生效**：preload 在进程启动时执行 ⇒ **当前实例仍是旧代码**，下次
  `./start-web.py` 启动才生效（不必为此专门重启，重启会掐断正在跑的会话）。
- **回退**：删掉 `connect: { family: 4 }` 一个片段即可。

## 七、没做的两档（以及为什么）

| 档 | 动作 | 为什么没做 |
|---|---|---|
| 系统层 | `/etc/gai.conf` 加 `precedence ::ffff:0:0/96 100` | 让 curl/git/pacman 也优先 IPv4。**需要 root**，而沙盒里 `sudo` 被 `no_new_privs` 挡住（`/etc/sudo.conf` 属主 65534）。要做由用户亲手执行一次；不做也不影响 DSH（DSH 的出境几乎全走 Node fetch） |
| 协议栈 | `sysctl net.ipv6.conf.all.disable_ipv6=1` | **不建议**。WSL2 mirrored 模式下 IPv6 接口镜像 Windows 侧，禁用是否生效不确定，且可能影响 Windows 网络；要重启 WSL。收益与档 1 重叠 |

## 八、如果将来还要上代理

不要用标准代理变量（会覆盖 dispatcher，IPv4/H1 一起丢）。正确形状是
「**按 host 分流的自建 dispatcher**」，写在同一处 preload 里：

```js
new Agent({
  allowH2: false,
  factory(origin, opts) {
    if (NEW Set(['opencode.ai']).has(new URL(origin).host)) {
      return new ProxyAgent({ ...opts, uri: 'http://127.0.0.1:PORT', allowH2: false })
    }
    return new Pool(origin, { ...opts, connect: { family: 4 } })
  },
})
```

配置走 `启动器配置和日志/当前配置.toml`（配置文件引入，不写死环境变量）；
代理层**不做重试**，失败冒泡成 `TRANSPORT` 交给已有的 `retryPolicy.maxRetries: 5`，
避免两层重试相乘成 25 次计费请求。

## 九、仍未定位的部分

本轮只把「建连」这一层钉住了（冷启动 8.4 s/超时 → 0.75–1.1 s）。
单请求 TTFB 仍有 0.9–1.5 s 落在「到 Cloudflare 的 RTT + TLS 握手」，这部分
IPv4 改不动；若「卡」还剩下，下一步要查的是**模型侧**耗时
（opencode-go 是跨境回源转发），工具是会话日志里的请求耗时分布，
不是 usage ledger（那里只有 token 数，没有时间）。

## 十、上线后的用户体感（2026-11-04 当晚）

重启实例后（运行记录 `20261104.215447-PID31438`，取证日志已确认
`"ipv4Only":true`，且 MCP 子进程同样带上），用户反馈「速度感觉快了不少」。

这一条只作**方向验证**，不作定量结论：体感混合了建连改善与当时的链路状况，
