# Practitioner survey: context compaction & recovering what it ate

Tags: **[S]** shipped+documented · **[B]** blog/announced only · **[P]** proposal, not shipped · **[M]** vendor marketing

## §1 Per-lab / per-product findings

### 1.1 Anthropic (strongest first-party published detail)
- **[B] Context engineering blog** — https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents
  - Compaction = "take a conversation nearing the context window limit, summarize its contents, and reinitiate a new context window with the summary."
  - Claude Code's compaction "preserves architectural decisions, unresolved bugs, and implementation details while discarding redundant tool outputs or messages. The agent can then continue with this compressed context **plus the five most recently accessed files**."
  - Explicit tuning guidance: "Start by maximizing recall to ensure your compaction prompt captures every relevant piece of information from the trace, then iterate to improve precision."
  - Two sibling techniques: **structured note-taking** (agent writes NOTES.md / a to-do list outside the window, re-read later) and **sub-agents** that "return only a condensed, distilled summary… often 1,000–2,000 tokens."
  - Cites context rot (Chroma) as justification: tool result clearing is "one of the safest lightest touch forms of compaction."
- **[S] Context editing API** — https://platform.claude.com/docs/en/build-with-claude/context-editing
  - `clear_tool_uses_20250919`: **defaults** `trigger` = **100,000 input tokens** (or N `tool_uses`), `keep` = **3 recent tool use/result pairs**, optional `clear_at_least` (token floor, to avoid cache-invalidation for nothing), `exclude_tools`, `clear_tool_inputs` (default `false`).
  - `clear_thinking_20251015`: `keep` = `{type:"thinking_turns", value:N}` or `"all"`; keeping thinking preserves the prompt cache.
  - **Server-side**: "Your client application maintains the full, unmodified conversation history. You do not need to sync your client state with the edited version." ← directly relevant: clearing is a *view*, your log stays whole.
  - Client-side SDK compaction exists as an alternative: "Generates a summary and replaces full conversation history" (TypeScript/Ruby, via `tool_runner`); docs say server-side is "generally preferred".
  - Context editing + memory tool combined: "When your conversation context approaches the configured clearing threshold, Claude receives an **automatic warning to preserve important information**" so it can write to memory files *before* the clear.
- **[S] Memory tool** — https://platform.claude.com/docs/en/agents-and-tools/tool-use/memory-tool
  - Tool entry is literally `{"type": "memory_20250818", "name": "memory"}`; client-side; all ops confined to a **`/memories`** prefix you map to storage (files, DB, cloud, encrypted files).
  - Commands: `view` (dir listing with human sizes, files 2 levels deep; ranged text views; text view truncates >**16,000 chars**; error at >**999,999 lines**), `create`, `str_replace`, `insert`, `delete`, `rename`.
  - "Claude automatically checks its memory directory before starting a task."
  - SDK helpers: `BetaAbstractMemoryTool` (Py/C#), `betaMemoryTool` (TS), `BetaMemoryToolHandler` (Java), local-FS impl `BetaLocalFilesystemMemoryTool`.
- **[B] Launch post (numbers)** — https://www.anthropic.com/news/context-management
  - Internal agentic-search eval: memory tool + context editing = **+39%** over baseline; context editing alone = **+29%**.
  - 100-turn web-search eval: context editing let agents finish workflows that otherwise failed, with **84% lower token consumption**. Public beta; Sonnet 4.5 adds token-budget awareness.
- **[S] Claude Code `/compact`** — https://code.claude.com/docs/en/how-claude-code-works (see "When context fills up") and https://code.claude.com/docs/en/context-window
  - Order of operations: "It clears older tool outputs first, then summarizes the conversation if needed."
  - Steer it: a **"Compact Instructions" section in CLAUDE.md**, or `/compact focus on the API changes`.
  - Anti-loop guard: "If a single file or tool output is so large that context refills immediately after each summary, Claude Code stops auto-compacting after a few attempts and shows an error" (thrashing).
  - **What survives compaction** (context-window doc table): system prompt/output style still apply; CLAUDE.md + unscoped rules **re-injected from disk**; auto memory re-injected; plan-mode plan re-injected; `paths:` rules and nested CLAUDE.md reload on file access; **files Claude read/edited: re-reads up to five, most recently modified first**; invoked skill bodies re-injected capped **5,000 tokens/skill, 25,000 total, oldest dropped first**; SessionStart hooks matching source `compact` re-run.
  - Partial compaction exists ("Summarize from here" / "Summarize up to here") — see §3 for its bug.
  - Tuning tip from official docs: "**Review what Claude remembers.** If you suspect context loss, ask 'What do you remember about X?'"
  - No published numeric auto-compact threshold found in official docs (they say "as you approach the limit").
- **[S] CLAUDE.md / auto memory** — https://code.claude.com/docs/en/memory
  - Two systems, both loaded every session: CLAUDE.md (you write: instructions/rules; managed-policy → user → project → local, load order broad→specific) and **auto memory** (Claude writes: learnings; **"first 200 lines or 25KB"** loaded).
  - "target under **200 lines** per CLAUDE.md file"; explicit framing: CLAUDE.md is "the place you write down what you'd otherwise re-explain."
- Third-party guide (not Anthropic) with the WHEN heuristic: https://github.com/MuhammadUsmanGM/claude-code-best-practices/blob/main/guides/context-management.md — compact when you finish a subtask, when tool output has piled up, or when responses slow down/"start forgetting"; "one concern per conversation"; "front-load important information so it survives compression."

### 1.2 OpenAI / Codex
- **[S] API-level compaction is documented**: https://developers.openai.com/api/docs/guides/compaction (page exists in the API docs nav; **I could not extract its body text** — see §4).
- **[S] Codex CLI has `/compact`** — https://github.com/openai/codex/issues/21468 (user report, 2026): running `/compact` alone prints `Context compacted` (`Context 100% left`); **the generated summary is not shown**, and `/compact [message]` does *not* trigger compaction (treated as a normal message) — the reporter compares unfavorably to Claude Code's `/compact [message]` focus and asks for `/compact --preview`.
- **[S] Server-side `/responses/compact`**: issue https://github.com/openai/codex/issues/22042 claims Codex CLI lacks a fallback when an OpenAI-compatible gateway doesn't implement `/responses/compact` (from the search-result snippet; I did not open the thread).
- **[P] "Compaction without summarization" RFC** — https://github.com/openai/codex/issues/8573 (status: **Draft**, maintainer-unimplemented). The most concrete handoff-style counter-design I found anywhere:
  - Reuse the CLI's existing `$CODEX_HOME/sessions/YYYY/MM/DD/rollout-*.jsonl` event log; derive a **`checkpoint_v1.json`** projection; compact = reset context + inject `view_v1(checkpoint, caps)`. "**No LLM is required to produce the checkpoint**" → "makes `/compact` usable even at 100% context usage."
  - Hard bounds: `maxFactsTotal=64`, `maxDecisionsTotal=32`, `maxPlanStepsTotal=32`, `maxRecentArtifacts=16`, `maxValueChars=160`; deterministic eviction (oldest by `lastTouchedSeq`, lexicographic tie-break).
  - Staleness is *derived*: a fact is `VALID` only if every dependency's artifact hash still matches, else **`SUSPECT`** — "guarantees no silent wrongness."
  - Output format is a fixed text block `[SESSION_CHECKPOINT v1]` with `[TASK] [PLAN] [RECENT_ARTIFACTS] [DECISIONS] [FACTS_VALID] [FACTS_SUSPECT]`; byte-stable, no token counting/heuristics/randomness; hashes recorded by the host, never the model; a `memory.apply()` tool can propose facts/decisions but is rejected without evidence refs and forbidden from storing behavioral policies.
  - Motivation quoted in the issue: post-compaction Codex "re-reads the same files, re-derives already known facts, loses awareness of recent edits," retaining "a lossy 'memento' summary instead of tool-call history."

### 1.3 Other coding agents
- **Cursor [B]** — https://cursor.com/en-US/blog/dynamic-context-discovery ("dynamic context discovery")
  - Long tool/MCP outputs are **written to a file** instead of truncated, agent `tail`s then reads more → "fewer unnecessary summarizations when reaching context limits."
  - The key recoverability move: "After the context window limit is reached, or the user decides to summarize manually, **we give the agent a reference to the history file**. If the agent knows that it needs more details that are missing from the summary, it can search through the history to recover them."
  - MCP tool descriptions synced to a folder; A/B test: **46.9% fewer total agent tokens** in runs that called an MCP tool (their number, high variance).
- **Cline [S]** — https://docs.cline.bot/features/auto-compact
  - Auto Compact: summarize → replace history → continue; claims it preserves technical details/code changes/decisions (marketing-flavored). Cost ≈ one tool call because input is prompt-cached. On non-supporting models it "falls back to standard rule-based context truncation."
  - Recoverability: **checkpoints let you roll back to before the summarization**; editing the message before the summarization call restores to that point.
- **Roo Code [S]** — https://docs.roocode.com/features/intelligent-context-condensing
  - "Intelligent Context Condensing" **enabled by default**; threshold slider (**default 100%**, docs elsewhere use 80% as an example) in Context settings; **custom condense prompt**; manual "Condense Context" button; slash commands in the first message are preserved across condensations; checkpoints to rewind (same caveat: "the summarized version is what's used in ongoing LLM calls").
- **Aider [S but different strategy]** — https://aider.chat/docs/repomap.html
  - No conversation summarization documented; instead a **repo map** (tree-sitter symbols) ranked by a graph-ranking algorithm over the file-dependency graph, clipped to a token budget (`--map-tokens`, **default 1k**, dynamically expanded when no files are in chat). Context control is via "add these files," not via summarization.
- **OpenHands [B + S]** — https://docs.openhands.dev/sdk/guides/context-condenser ; https://openhands.dev/blog/openhands-context-condensensation-for-more-efficient-ai-agents
  - Default `LLMSummarizingCondenser` (extends `RollingCondenser`/`CondenserBase`): triggers when events exceed `max_context_length`, **always keeps the first `keep_first` events** (system prompt, initial user messages), summarizes the middle.
  - Summary prompt is goal-oriented: "the user's goals, the progress the agent has made, and what still has to be done… critical files and failing tests."
  - Numbers: "up to **2x** per-turn API cost reduction"; on a SWE-bench Verified subset condensation solves **54%** vs baseline **53%**; scaling goes from quadratic to linear. Condensation is deliberately deferred to a size threshold to amortize prompt-cache rebuilds.
- **Devin / Cognition [B]** — https://cognition.ai/blog/dont-build-multi-agents
  - Principles: "Share context, and share **full agent traces, not just individual messages**" and "Actions carry implicit decisions."
  - Explicitly pro-compaction but anti-naive: for very long tasks "we introduce a new LLM model whose key purpose is to compress a history of actions & conversation into key details, events, and decisions. **This is hard to get right**… Depending on the domain, you might even consider **fine-tuning a smaller model** (this is in fact something we've done at Cognition)." No thresholds published.
- **Continue [unverified]** — https://docs.continue.dev/cli/tui-mode ; only found a CLI context-length/truncation PR (https://github.com/continuedev/continue/pull/9467). No documented compaction feature I could confirm.

### 1.4 Memory products / frameworks
- **Letta / MemGPT [S + M]** — https://docs.letta.com/v1-sdk/memory/memory-blocks/ ; https://docs.letta.com/v1-sdk/messages/compaction/ ; https://www.letta.com/blog/sleep-time-compute
  - **Memory blocks**: structured, *always-visible* sections prepended to the prompt as XML (`<memory_blocks><persona>…<metadata>- chars_current=128 - chars_limit=5000</metadata><value>…`). Each block = `label`/`description`/`value`/`limit` (chars). Agent edits them with built-in tools; blocks are the core abstraction and can be shared across agents.
  - **Compaction defaults**: mode `sliding_window` (summarize oldest **~30%** — `sliding_window_percentage=0.3` — keep ~70%, growing in ~10% steps if needed), `clip_chars` **50,000** summary cap, summarizer defaults `claude-haiku-4-5` / `gpt-5-mini` / `gemini-2.5-flash`, modes also include `all`, `self_compact_sliding_window`, `self_compact_all` — the self-* modes exist specifically to preserve prefix-cache hits.
  - **Sleep-time compute** (arXiv 2504.13171): run a separate agent while idle to reorganize memory; the blog frames memory editing as a background job rather than a pre-context-loss scramble.
- **Mem0 [M, paper]** — https://arxiv.org/abs/2504.19413
  - Extraction/consolidation/retrieval over LOCOMO; **26% relative** LLM-as-judge improvement over OpenAI's memory; graph variant ~2% higher overall; **91% lower p95 latency** and **>90% token cost** vs full-context. Self-reported.
- **Zep / Graphiti [M, paper]** — https://arxiv.org/abs/2501.13956
  - Temporal knowledge graph (edges carry validity intervals). Deep Memory Retrieval: **94.8% vs MemGPT 93.4%**; LongMemEval: accuracy improvements **up to 18.5%**, latency **−90%**. Self-reported.
- **Redis Agent Memory Server [S, closest off-the-shelf analogue to the engineer's design]** — https://github.com/redis/agent-memory-server/blob/main/V0/docs/working-memory.md
  - Working memory = current session, stored as **Redis JSON**, fields `messages`, **`context` (the summary of older messages)**, `memories`, `data`, `user_id`, `namespace`, `ttl_seconds`.
  - Auto-summarization fires at **default 70% of the context window**; older messages are summarized into `context`, then **removed**; recent messages kept intact; `WorkingMemoryResponse` exposes context usage %. Structured `memories` are additionally indexed into long-term, searchable storage. No search over working memory itself.
- **LangMem [S]** — https://github.com/langchain-ai/langmem/blob/main/docs/docs/guides/summarization.md
  - `summarize_messages()` + prebuilt `SummarizationNode`; a `RunningSummary` is carried in graph state and passed back in on the next call (incremental/rolling summary); knobs `max_tokens`, `max_tokens_before_summary`, `max_summary_tokens`.
- **Basic Memory [M]** — https://github.com/basicmachines-co/basic-memory : markdown files on local disk + knowledge graph, exposed over MCP; README is marketing, no architecture/eval detail verified.
- **Cognee / OpenMemory** — https://docs.cognee.ai (graph memory pipeline), https://mem0.ai/blog/introducing-openmemory-mcp (Mem0's local memory MCP server). Existence verified; internals/evals **not** verified.

### 1.5 Community & individual practice (incl. the anti-summarization camp)
- **CodeWhale #664 — "Context-limit handoff as a default replacement for routine compaction" [P]** — https://github.com/Hmbown/CodeWhale/issues/664 (maintainer design exploration, filed 2026-05-04, not implemented)
  - Mechanism: at ~**80%** of the window the agent writes a structured handoff and the engine spawns a **fresh agent loop** seeded with it, so the handoff becomes the successor's stable cache prefix. Staged prompts: ~70% "consider wrapping up," ~80% "draft a handoff," ~90% "stop and hand off now."
  - Handoff artifact: **`.deepseek/handoff.md`** (stated to already be a real path via `prompts.rs::HANDOFF_RELATIVE_PATH`), sections: Goal / Current state / Open blockers / Recent decisions / Files-of-interest / **Recovery hints (commands to re-discover state if anything's missing)**.
  - The anti-compaction argument is **cost, not accuracy**: compaction creates a byte-different prefix, so the cache misses — "on an 800K-token-prefix session, that's roughly a **10× cost spike on the post-compaction turn**."
  - Honest risk list: producing a good handoff is itself expensive; UX seam visible to the user; "single-thread deep debugging can't be cleanly chunked" → **hybrid fallback to compaction**.
- **Handoff (Rust CLI) [S, small tool]** — https://github.com/TStansel/handoff
  - `handoff codex claude` reads local Codex/Claude Code/Cursor Agent session transcripts, writes **`.agent-handoff/latest.md`**, then launches the target agent. Flags: `--repo` (git branch/commit/changed files/snapshot), `--include-raw` (copies raw transcript into `.agent-handoff/raw/`), `--history` (timestamped archive), `--inject` (adds a marked pointer block to `CLAUDE.md`/`AGENTS.md`), `--session <id|path>`. Recommends gitignoring `.agent-handoff/`. Cursors sessions read from `~/.cursor/projects/<key>/agent-transcripts/<id>/<id>.jsonl`.
- **Claude Code's own issue tracker — where the recoverability problem actually bites [S, user reports]**
  - https://github.com/anthropics/claude-code/issues/57636 — manual `/compact` **discards the original conversation before confirming the summary API call succeeded**. On a 401 the continuation contains only the raw error text; `compactMetadata` recorded `postTokens=8471`, `durationMs=1498` vs 88–120s for real compactions, i.e. **the metadata masked the failure**. v2.1.112.
  - https://github.com/anthropics/claude-code/issues/92347 — partial compaction "Summarize up to here" **silently drops prior compact-summary messages** that sit after the anchor (client filters `entry.type==="user" && entry.isCompactSummary` when rebuilding the preserved suffix). "The entries remain in the session's `.jsonl` transcript file, but the live context loses them permanently." Since a summary is the only in-context representative of hundreds of compacted messages, decisions/task state/pending work vanish with no warning. Reproduced across four cuts / three sessions, v2.1.246–2.1.259. Workaround: use `/compact` or "Summarize from here."
  - Read together: the append-only transcript **is** the recovery path, but the agent doesn't surface it — both bugs are "recoverable in principle, unrecoverable in practice."
- **Chinese-language sources**
  - 腾讯云开发者 **[B/M]** — https://cloud.tencent.cn/developer/article/2673955 : "上下文卸载 + Mermaid 无限画布" — offload full logs to an external file system while keeping a high-density structured (Mermaid) skeleton of task state in context.   - 知乎 **[B/community]** — https://zhuanlan.zhihu.com/p/2070164053067043659 ("从零学Agent·阶段六") frames it as **Context Triage → Semantic Compaction → Progressive Discovery**, i.e. classify before compressing rather than blindly summarizing. ### 1.6 The counter-position: long context degrades → retrieval/summarization is the rational default
- **Chroma "Context Rot" [research]** — https://research.trychroma.com/context-rot
  - Controlled sweeps over **18 LLMs** holding task complexity constant while varying only input length. NIAH is "fundamentally a simple retrieval task… direct lexical matching"; with semantic (non-lexical) matching, distractors, absence detection, and a conversational QA task using **LongMemEval**, "even under these minimal conditions, model performance degrades as input length increases, often in surprising and non-uniform ways." Code: https://github.com/chroma-core/context-rot. Implication: don't wait for bigger windows; curate.
- **Anthropic's own position [B]** — the context-engineering post asserts LLMs have a finite "attention budget," that context is "a finite resource with diminishing marginal returns," and that "context windows of all sizes will be subject to context pollution and information relevance concerns" — i.e. a first-party lab arguing against the "just use the long window" counter-counter.
- **Evidence that compaction is often *good enough* [M/B]** — OpenHands 54% vs 53% on SWE-bench Verified; Anthropic's +29%/+39% and −84% tokens; Cursor's claim that file-izing tool output means *fewer* summarizations; Letta shipping compaction on-by-default with generous defaults (50k-char summaries). None of these measure *what was lost*; they measure task success and cost.

## §2 Cross-cutting patterns (what converges, what doesn't)

1. **Everyone compacts; nobody deletes the source.** Anthropic's context editing is explicitly server-side ("your client application maintains the full, unmodified conversation history"); Claude Code keeps everything in the session `.jsonl`; Codex CLI keeps `rollout-*.jsonl`. The full transcript surviving compaction is the industry norm — the *recovery affordance over it* is the rare part.
2. **The most-implemented recovery affordance is "give the agent a file handle, not a summary."** Cursor hands the agent a **reference to the history file** and lets it search; Cursor/Anthropic both convert big tool outputs into files the agent can `tail`/`read`/`grep`; Claude Code re-reads up to **five most-recently-modified files** after compaction. Handoff-style tools (`.agent-handoff/latest.md`, `.deepseek/handoff.md`) are the same idea with a human-readable artifact.
3. **Thresholds cluster at 70–80% of the window.** Redis working memory auto-summarizes at **70%**; Anthropic context editing defaults to a **100,000 input token** absolute trigger; Roo's slider defaults to 100% (80% given as an example); CodeWhale proposes 70/80/90% staged prompts. Absolute-token and percentage triggers are both common — no consensus.
4. **Keep-recent-N + summarize-the-tail is universal** (Anthropic `keep: 3 tool uses`; Letta `sliding_window_percentage=0.3`; OpenHands `keep_first` + `max_context_length`; Cline/Roo replace history with a summary; Codex "Context 100% left").
5. **Tool results are the first thing to go; conversation/prose is last.** Anthropic clears tool outputs *before* summarizing; Cursor converts them to files; OpenHands/Roo/Cline summarize prose as a second step. Near-universal agreement that tool output is the cheapest thing to sacrifice.
6. **A hierarchy of things that are re-injected from disk rather than summarized.** Claude Code re-injects CLAUDE.md, auto memory, the plan, path-scoped rules, and skill bodies. Letta's memory blocks are always-visible and never retrieved. The pattern: *durable state lives in files; only the conversation is summarized.*
7. **A separate/cheaper model does the summarizing, and cache behavior drives the design.** Letta defaults to haiku/gpt-5-mini/gemini-flash and offers `self_compact_*` modes purely for prefix-cache compatibility; OpenHands defers condensation to a size threshold to amortize cache rebuilds; CodeWhale argues the cache miss is the real cost. Cognition says the compaction model is important enough to *fine-tune*.
8. **Prompt-customizable compaction is now table stakes**: Claude Code `/compact <focus>` + a "Compact Instructions" section in CLAUDE.md; Roo "Custom Context Condensing Prompt"; Letta `compaction_settings.prompt`; LangMem explicit `max_*` knobs. Codex CLI is the outlier (issue #21468 explicitly notes the summary is invisible and `/compact [msg]` silently no-ops).
9. **Two camps on *where* compaction should happen** — first-party labs want an LLM summary that reads as continuity (Anthropic, Cursor, Cline, Roo, OpenHands, Letta); the dissenters want *deterministic state*, no LLM in the loop: Codex RFC #8573 (`checkpoint_v1.json`, host-computed hashes, `SUSPECT` staleness, "no LLM is required… works at 100% context") and Tencent's "offload the full log, keep a Mermaid skeleton."
10. **Rollback ≠ recovery.** Cline and Roo both advertise "checkpoints" as the answer to summary loss — but that rewinds the whole session; it does not let you *look up* what the summary dropped while carrying on. Nobody in this survey ships "compaction summary + searchable archive of the region it replaced" as one coherent feature. That is exactly the gap described in §3.

## §3 Explicit contradictions / who says what against whom
