# 等待归因实验：一次「猜错的瓶颈」与 188 倍提速

文件名: 用户笔记/检索/等待归因实验-dsh_message嵌入写回.md
摘要: dsh_message 向量化任务长期只跑到 TPM 19%。我先猜「server_bge 的串行锁」，
      再猜「上游文本更长」——**两次都错**。插上三段打点后真凶现形：
      数据库写回占 73.4%（11.7 秒/批），根因是 body_sha256 缺索引导致每条
      UPDATE 全表扫 14 万行。加索引后写回降到 62 ms，TPM 从 19% 升到 69–83%。
日期: 2026-10-25
关联: `server_bge-v2-公平限流队列设计.md`（同源方法论）、`tools/lane-a-embed-messages.py`

---

## 一、为什么要做这个实验

任务本身很简单：给 `dsh_message` 的 2.7 万条对话正文算 embedding，走现有
`server_bge` 转发到硅基流动的 `bge-m3`。配额的纸面额度是 RPM 2000 / TPM 500k。

**实际只跑到 TPM 19%**，预计要 74 分钟。于是我开始归因……

## 二、两次猜错

### 第一猜：server_bge 的串行锁

推理很顺：`RateLimiter.acquire` 里有 `async with self._serial:` 一把全局锁，
把并发压成单路 → 吞吐上不去。

**为了验证**，把客户端并发从 6 提到 16：**没有任何提升**。

### 第二猜：上游处理时间 × 文本更长

改测单请求：proxy 转发 batch=32 只要 **1.0 s**（2003 条/分钟），
直连 `api.siliconflow.cn` 要 **270 s**（7 条/分钟，差 285 倍，用全新随机文本排除缓存）。

于是判断「真实文本平均 583 字符，是测试样本 240 字符的 2.4 倍，所以慢是应该的」。

**这个推理听起来合理，但它没有证据**——只是把两个数字凑出了解释。

## 三、插上打点，真凶现形

给脚本加三段计时（全部同进程 `monotonic()`，可安全相减）：

| 段 | 含义 |
|---|---|
| **gate** | 我们自己**主动**限速睡的时长 |
| **http** | 端到端 HTTP 往返（含 server_bge 内部排队 + 上游处理） |
| **db** | 回写 MariaDB |

第一次输出：

```
归因 限速 4.1% · HTTP 22.5% · 写回 73.4%
每批均值 限速 0.66s / HTTP 3.60s / 写回 11741.8ms
HTTP P50 4.10s P95 6.62s
```

**73.4% 的时间花在数据库写回，每批 32 条要 11.7 秒。** 不是锁，不是网络，不是限速。

## 四、根因：缺一个索引

```sql
UPDATE dsh_message SET embedding = VEC_FromText(?), embedded = 1
WHERE body_sha256 = ?
```

`body_sha256` **没有索引** → 每条 UPDATE 全表扫 14 万行（385 ms），
一批 32 条 = 12.3 秒。而且 `autocommit=ON` 让它变成 32 次独立全表扫。

**但「全表扫」这个说法还太糙，再挖一层**（2026-10-25 追加实测）：

| 观测 | 值 | 说明 |
|---|---|---|
| `Innodb_buffer_pool` 命中率 | **99.73 %** | 几乎没有物理读 |
| 表大小 vs 缓冲池 | 2381 MiB vs **8192 MiB** | 整张表常驻内存 |
| 全表 `COUNT(*)` | **42.75 ms** | 走索引，不读行 |
| 无索引 UPDATE | **385 ms** | 要读整行内容 |

所以这 **385 ms 既不是磁盘、也不是 9P**（MariaDB 跑在 Windows 侧，数据在
`E:\`，原生 NTFS，架构上早已排除 9P 这个变量）。

它是**在内存里扫 2.4 GB 宽行**的 CPU/内存带宽成本：

```
2381 MiB / 140,866 行 ≈ 17 KB/行   （其中 4 KB 是 VECTOR(1024) 向量列）
2.4 GB / 385 ms ≈ 6.2 GB/s          ← 内存带宽量级
```

旁证就是 `COUNT(*)` 与 UPDATE 的 9 倍差：前者走索引不读行，后者必须把含
4 KB 向量的整行搬出来解析。

**教训升级版**：所有人都会默认「数据库慢 = 磁盘慢」。这次连磁盘都不是，
是 CPU 在搬内存。归因必须落到具体资源上，不能停在「存储层」这种粗粒度。

排查过程中还踩了两个陷阱：

- **`SET embedded = embedded` 测出 389 ms** —— 这是「无变化更新被优化掉」的反面：
  它没能优化掉扫描，但也没真正写。用这种语句测写入性能会得出错误结论。
- **`SET embedded = 1 - embedded` / `SET embedding = embedding` / 真写 4KB 向量
  三者都是 0 ms/条** —— 加索引之后，这些才恢复成正常速度。所以「哪个列慢」
  这个问法本身就有问题，**慢的是「找不到行」**。

### 修复

```sql
ALTER TABLE dsh_message ADD INDEX idx_body_sha256 (body_sha256);   -- 0.65 s
```

## 五、修复后的归因

```
归因 限速 9.1% · HTTP 88.8% · 写回 2.0%
每批均值 限速 0.28s / HTTP 2.72s / 写回 61.8ms
HTTP P50 2.44s P95 5.48s
```

| 指标 | 修复前 | 修复后 | 变化 |
|---|---|---|---|
| 写回占比 | 73.4% | **2.0%** | — |
| 写回/批 | 11,741 ms | **62 ms** | **188×** |
| TPM 占用 | 19% | **69–83%** | 贴近 85% 目标 |
| 预计总时长 | 74 min | **16 min** | 4.6× |

## 六、教训

1. **没有分段打点就不要断言瓶颈在哪。** 我两次「合理推理」都错，
   而且错得很像对的——因为它们能把观测到的数字解释圆。
   「能自圆其说」不等于「是证据」。

2. **瓶颈常常不在你以为的那一层。** 讨论了半天调度器、限流、并发、
   AIMD，真凶是一个 `ALTER TABLE ... ADD INDEX`，0.65 秒解决。

3. **`SET col = col` 这种「无变化更新」不能用来测写入性能**——
   它可能被优化掉，也可能只是省了索引维护，但扫描照做。

4. **跨机段不能用时间戳相减。** 本例中客户端 → server_bge 是同机（可相减），
   server_bge → 上游是跨机（只能用往返 RT）。三段打点之所以可信，
   是因为它们全在客户端进程内用 `monotonic()` 测——**不跨机、不自比**。

5. **先诊断，再优化。** 如果按第一猜（拆串行锁）或第二猜（加并发）动手，
   会改出一堆复杂度而性能纹丝不动——因为瓶颈根本不在这两处。

## 七、这次实验的方法论出处

同源讨论见《从 DeepInfer 到打点计时：一个 XP 老登的 AI Infra 词汇翻译、
等待归因与同时性漫游》（`对话/非折腾记录/` 下的会话归档）：

> 当年看那个等待时间，是看到底卡 CPU 了，卡内存了，还是卡磁盘子了

> 打点计时和分布式系统的性能统计是一个东西

这次正好把这条老手艺在现代场景里跑了一遍：**粗插杆子、打时间戳、
分段归因**——不需要 gprof，\(三段 `monotonic()`\) 就够了。

## 附：为什么 `HTTP` 段仍有 88.8%

因为该段把「server_bge 内部排队 + 上游处理」打包在一起了。要进一步细分，
需要 `server_bge` 自己吐分段耗时（`Server-Timing` 响应头是现成载体，
W3C 标准，见 `server_bge-v2-公平限流队列设计.md` §5.6）。

当前 HTTP P50 2.44 s / P95 5.48 s，与 batch=32、平均 583 字符的预期基本吻合
（probe 用 240 字符样本测得 1.0 s，按长度比例外推约 2.4 s）——
所以这一段大概率是**上游处理时间**，不是排队。但这仍是推断，
等 `Server-Timing` 落地后才能定论。
