## 〇、为什么必须有一个转发器（第一性原理）

用户 2026-10-25 的原话：

> 为什么要设计这么一个转发器呢，是因为上游对 RPM、TPM 以及其他可能的并发限制的结算，
> 他**只认 key**。既然上游就这么认的，那我们确实需要一个中央协调机构把这堆问题管起来。

推理链是严密的，且决定了整个架构的必然性：

```
上游按 API key 结算配额（RPM / TPM / 并发）
        ↓
同一个 key 的所有调用点共享同一个配额池
        ↓
若多个客户端各自直连，各算各的 → 配额池被多方竞争 → 超限 429
        ↓
∴ key 的调用点必须集中 —— 转发器不是设计偏好，是必要条件
```

**推论一：客户端直连是错的**。不是「慢」的问题，是**令出多门**——每个客户端都以为自己只用了一点点，合起来早就爆了。2026-10-25 实测直连比转发慢 285 倍，那是网络路径的巧合；**即使直连更快，它依然是架构上错的**。

**推论二：转发器是配额的唯一权威（single source of truth）**。它必须知道全局用量，否则任何限流都是瞎猜。这也意味着 **AIMD 只能放在转发器里**——只有它观测得到全局的拒绝率和延迟。

**推论三：权力与责任对等**。既然转发器垄断了出口，它就必须承担**队列、公平、背压、可观测**的全部责任。串行锁只保住了「公平」一项，把「吞吐」和「可观测」丢了——这才是要改的地方，不是要取消转发器。

**推论四：单点是代价，队列是解药**。集中必然带来单点故障域与单点瓶颈。业界对付它的办法不是「去掉中心」（那会失去配额纪律），而是**有界队列 + 明确背压 + 快速失败**——让排队可见、可控、可拒绝，而不是让客户端阻塞着赌运气。

这也是分布式限流最后都收敛到 Redis / Envoy 这类**集中式令牌桶**的原因：**结算粒度在哪，限流器就必须在哪**。

## 一、现状与设计意图

`server_bge.py` 的 `RateLimiter.acquire`：

```python
async with self._serial:
    while True:
        ...检查令牌...
        await asyncio.sleep(...)    # ← 睡在锁里
```

**这不是疏忽，是用户 2026-10-25 明确的设计选择**：

> 让上游等是我故意的设计，这样近似尽力 FIFO，避免饥饿。说白了，这事儿是跟 IRP 队列学的。

所以评价它必须先承认这个前提：**它要的是「序」，不是「吞吐」**。
饥饿比慢难排查——慢是均匀的，饥饿是偶发的、看运气的。

问题不在「等」，在于**「等的时候把整个队列冻住了」**：队首在锁内 sleep，
后来者连入队（查一下能不能扣）都做不到。

## 二、IRP 队列的真正形状：排队 ≠ 阻塞

Windows 内核的 IRP 队列，关键不在 FIFO，而在**排队与执行是分离的**：

1. I/O 管理器收到 IRP → **挂到设备队列** → 立刻返回（线程不占用）
2. 设备就绪 → **按队列顺序**取出 → 派发
3. 完成后走 completion routine **回调**唤醒请求方

「序」由队列保证，「等」不占用任何执行资源。这两件事被解耦了。

**当前实现把它们粘在一起**：为了保住队首的序，把整条队列冻住。

## 三、实践中的现成范式（可直接抄的）

| 范式 | 出处 | 与本问题的关系 |
|---|---|---|
| **`limit_req` = 漏桶 + 队列 + burst** | Nginx | **最接近的现成实现**：`rate=10r/s` + `burst=20`（队列深度）+ `nodelay`；超队列 → **503**。我们的 `RateLimiterBusy` 就是它的 503 |
| **`AsyncLimiter`** | Python `aiolimiter` | 用 `asyncio.Condition` 实现，**唤醒顺序即 FIFO**（Condition 的等待队列天然有序）——这就是「不冻队列的 FIFO」的标准写法 |
| **Guava `RateLimiter`** | Java | SmoothBursty / SmoothWarmingUp，令牌桶 + 平滑；但**不做 FIFO**，调用方自己排队 |
| **GCRA（Generic Cell Rate Algorithm）** | Redis Cell | 精确速率 + 无突发，用「理论到达时间」TAT 单值表示整个桶状态，无队列 |
| **Fair Queueing / WFQ** | 网络调度 | 按**流**公平（per-flow），不是按请求顺序；不适用于单租户 |
| **Async Request-Reply Pattern** | Azure Architecture Center | 官方范式：202 Accepted + 状态轮询 + Retry-After |
| **Token Bucket**（基础） | 通用 | 只解决「速率上限」，不解决「顺序」与「等待」 |

**结论**：不需要发明。`aiolimiter` 的 `Condition` 写法 + Nginx `limit_req` 的「队列深度 + 超限即拒」就是完整答案。

### 一个关键区别（Loyola 的 token bucket 章节指出的）

> fair queuing 与 token bucket 的实际差别在于：某个发送方空闲时，fair queuing 会把带宽让给别人，token bucket 不会。

对应到我们：**空闲时段攒下的令牌要不要允许突发**。当前实现按滑动窗口算（不允许跨分钟突发），这是保守且正确的——上游的 TPM 也是按分钟窗口计的。

## 四、HTTP 这一头的固有局限（用户的观察）

> 我怀疑 HTTP 这一头很大一个问题，就是没有一个类似于事件对象这样的叫醒和通知机制。

**这个判断是对的，且是协议层的**。HTTP 是「请求-响应」：客户端发起、服务端回答。
服务端**没有主动通知客户端的通道**——除非客户端预先维持一条连接（SSE/WebSocket）或留一个回调地址（Webhook）。

后果：**「排队等待」在 HTTP 下必然占用一条连接/一个协程**。无法像 IRP 那样
「挂起请求 → 释放资源 → 完成时回调唤醒」。

业界的四种绕法：

| 手段 | 机制 | 代价 |
|---|---|---|
| **长轮询** | 客户端发请求，服务端 hold 住直到有结果或超时 | 占连接；AWS SQS 用 20 s |
| **202 + 轮询** | 立即回 202 + Location，客户端按 `Retry-After` 来查 | 轮询开销、延迟抖动 |
| **Webhook** | 服务端完成后反向 POST 客户端 | 客户端需可被访问（公网地址） |
| **SSE / WebSocket** | 建立长连接，服务端推送 | 状态管理复杂，不适合纯请求-响应 API |

**对 server_bge 的启示**：它本身就是本地 HTTP 服务，最务实的是
**202/503 + `Retry-After` + 队列位置**，让客户端立刻知道「要等多久」，
而不是阻塞在连接上赌它不会超时。

补充：HTTP/1.1 有一个接近「握手确认」的机制——`Expect: 100-continue`
（客户端问「能收吗」，服务端回 100 或 417），但它只用于请求体上传，不适用于排队。

## 五、v2 设计形状

### 5.1 核心：叫号，而不是锁上排队

```python
class FairGate:
    """按到达顺序派发；队首等待期间不持有任何锁。"""

    def __init__(self, tpm, rpm):
        self._q = deque()                  # [(tokens, future)]，严格 FIFO
        self._lock = asyncio.Lock()        # 只保护入队/出队，微秒级
        self._tokens = ...                 # 令牌桶（滑窗）

    async def acquire(self, tokens):
        fut = asyncio.get_running_loop().create_future()
        async with self._lock:
            self._q.append((tokens, fut))
            first = len(self._q) == 1
        if first:
            asyncio.create_task(self._pump())
        await fut                          # 只等自己的号

    async def _pump(self):
        while True:
            async with self._lock:
                if not self._q:
                    return
                tokens, fut = self._q[0]
            wait = self._need(tokens)
            if wait > 0:
                await asyncio.sleep(wait)  # ← 睡在锁外
                continue
            async with self._lock:
                self._q.popleft()
                self._take(tokens)
            fut.set_result(None)
```

**FIFO 强度不降反升**（deque 是显式的序），并且：

- 新请求可立即入队拿到号
- `len(self._q)` 成为**背压的观测点**
- 排队时长可预估 → 可在**入队时**判定「按当前队列要等 130 s > 你的 60 s 上限」，立即拒绝，而不是等满 60 s 才报 busy

### 5.2 装满：消费者要多开，令牌桶要共享

单消费者 = 单请求打上游，吞吐受「单请求耗时」限制。要真正装满 TPM，
必须**多消费者并发打上游 + 一个共享令牌桶**：

```
生产者（HTTP 请求）→ 有界队列(maxsize) → N 个消费者
                                            ↓
                                  共享 FairGate（锁内只扣减）
                                            ↓
                                        上游 API
```

「防令出多门、污染配额池」的正解就在这里：**配额池单点，出口多点**。
锁保护的是「扣减」这一个原子操作（微秒），不是「发送」（秒级）。

### 5.3 消费者开几个：AIMD 探测（用户指定）

消费者数**不该拍脑袋定死**。用户给的做法是多线程下载器的经典套路：

> 先开到指定的最高进程，然后看被没被拒，被拒了就减少。

这就是 **AIMD**（Additive Increase / Multiplicative Decrease），TCP 拥塞控制的家族，
也是 Netflix `concurrency-limits` 的核心思想：

```
成功（无 429/503）：  limit += 1/limit      ← 加性增，慢爬
被拒（429/503）：     limit *= 0.5          ← 乘性减，快退
```

为什么是「加性增、乘性减」而不是反过来：**慢爬快退**。爬得太快会在超限边缘震荡，
退得慢会把上游打到雪崩。TCP 四十年前就学到了这一课。

#### 与令牌桶的分工：两个正交的控制

| 控制 | 管什么 | 依据 |
|---|---|---|
| **令牌桶（FairGate）** | 你**被允许**用多少 | 上游公布的 TPM/RPM |
| **AIMD** | 你**实际能**用多少 | 上游的实时反应（429/延迟） |

配额是「纸面上的」，实际上游可能因为共享池、路由、模型冷启动而给不到。
AIMD 补的就是这个差值——**令牌桶保证不违规，AIMD 保证不浪费**。

#### 判据用哪个信号

三个可选，按可靠性排：

1. **429/503**（显式拒绝）—— 最可靠，现在就能用
2. **延迟梯度**（Netflix Vegas 式）—— 无拒绝但延迟陡增时提前退，比等 429 早一步
3. **超时** —— 最迟钝，只在真正卡死时反应

初版只用第 1 个（简单可靠），第 2 个可以在有稳定延迟基线后加。

#### 别忘了上限

AIMD 要有一条**天花板**（下载器的「指定最高进程数」）。
没有天花板的话，上游如果不返回 429（比如它对并发不敏感、只按速率限），
limit 会一路加到你自己的资源耗尽。建议 `MAX_CONCURRENCY` 显式配置，默认 8。

### 5.4 对外接口：202 / 503 + Retry-After

因为 HTTP 没有事件通知，接口要主动把「等多久」告诉客户端：

- 队列未满 → 正常处理
- 队列满 或 预估等待 > 客户端容忍 → **503 + `Retry-After: N`**
- 或 202 + 任务 id（如果将来做异步化）

### 5.5 要动的代码位置

| 位置 | 改动 |
|---|---|
| `RateLimiter.acquire` | 换成 `FairGate`（锁内只扣减，sleep 在锁外） |
| `_embed_remote` | acquire 之前先入队，拿到号再发 |
| `/v1/embeddings` | 503 时带 `Retry-After`；可选 202 异步模式 |
| 配置 | `EMBED_QUEUE_MAX`（队列深度，对应 Nginx 的 burst） |

## 六、风险与取舍

- **队列深度是双刃剑**：深则吞吐稳定但延迟高；浅则响应快但频繁拒绝。
  默认取 Nginx 的思路——`burst` 显式配置，超出即 503，**不搞无限队列**。
- **多消费者会改变上游看到的节奏**：从「均匀慢」变成「并发冲击」。
  如果上游对并发敏感（有明显 429），消费者数要保守起步（2–4）。
- **FIFO 只在单进程内成立**：多 worker（多 UVicorn 进程）时各进程有各自的队列，
  序就散了。当前是单进程双端口线程，成立；将来若多进程需换 Redis 等集中式令牌桶。

## 附：2026-10-25 的一个实测纠正

一度把「TPM 只跑到 17%」归因于服务端串行锁。实测推翻了：

| 路径 | batch=32 耗时 | 吞吐 |
|---|---|---|
| 经 server_bge 转发 | **1.0 s** | **2,003 条/分钟** |
| 直连 `api.siliconflow.cn` | 270 s | 7 条/分钟 |

差 285 倍，且用全新随机文本复测排除缓存。所以**直连慢是本机到该域名的网络路径问题**
（大概走了代理），不是并发能力问题。真实文本平均 583 字符（测试样本 240 的 2.4 倍），
所以实际速率约 235 行/分钟——瓶颈是**文本长度 × 单路处理时间**。
