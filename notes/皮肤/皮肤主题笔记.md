# dsh UI 定制速查（2026-08-30 沉淀，含宽表格/标题/分割线实战）

## 三条路

| 想改什么 | 去哪改 | 怎么生效 |
|---|---|---|
| **某个皮肤特有的视觉**（颜色/对比度/chip） | `dsh-domus/skins/<id>/patches.css` | 重载页面即可（运行时资产，皮肤 CSS 强制作用域 `html[data-dsh-skin="<id>"]`） |
| **所有主题都要生效**的视觉/布局 | `dsh-font-serif/lib/client.js` 的 FONT_CSS 数组（插件注入 `<style>`） | 重启 dsh web + Ctrl+F5（Firefox 硬刷新） |
| 组件结构/行为 | 基本别碰（官方源码是 monorepo，patch 成本高） | —— |

## 选择器三条铁律

1. **优先用 DOM 里的 `data-*` 锚点**：`data-dsh-part`、`data-dsh-responsive-part`、`data-slot`、`data-pane`——语义属性，不随构建变，跨主题稳定
2. CSS Module 哈希类名（`WyiL6q_crumb` 这种）外部**选不中**，用 `[class*="crumb"]` 子串匹配
3. 拿不准就结构选择器兜底：`> nav` / `> div`（注意 titleCluster 的直接子 div 就是 headerActions，nav 是 crumbs）

## 高频坑（实战踩过）

- **`overflow` 对 `display: table` 元素无效**（CSS 规范：只适用于块/flex/grid 容器）——表格滚动必须靠包裹 div，`<table>` 本身加 overflow 永远无效
- **"看不见"先查 token 再查 CSS**：皮肤会重映射官方 token（furina 把 `--dsw-alias-border-l2/l3` 重映射成低透明度深蓝 `#2c3a7338`），表格分割线暗底隐形是 token 的锅，不是没生效
- **滚动条可能"存在但隐形"**：官方 `scrollbar.css` 给 Firefox 走 `scrollbar-width: thin` + 暗色 thumb，暗底上肉眼不可见——先查 `scrollbar-width/scrollbar-color` 再下结论
- **宽表格溢出别信滚动条**：官方 breakout 把 `.md-table-wide` 容器撑到整个 transcript 宽（100cqw、`max-width: none`），表格常不溢出；滚动方案在 Firefox 不可靠，最终用强制压缩（见下）
- **按钮/元素限宽导致截断**：`.crumb { max-width: 220px; text-overflow: ellipsis }` 这类"防撑爆"设计会掐长标题——先查 max-width 再怀疑布局

## 实战成果（都在 dsh-font-serif 插件或 navia/patches.css）

| 改动 | 位置 | 要点 |
|---|---|---|
| 宽表格强制压缩 | client.js `.md-table-wide` 块 | 容器 `width: calc(100% - 16px)` + `margin/padding-left: 0`；table `width:100%` + `table-layout: auto`（按内容量分配列宽）；th/td `white-space: normal` + `overflow-wrap: anywhere` 杜绝溢出 |
| 表格分割线加亮 | client.js（furina/navia 限定） | `html[data-dsh-skin="furina"/"navia"] [data-dsh-part="message-row"] table th/td` 半透明白（th 0.35 / td 0.22） |
| 标题居中 + preset 标签左对齐 | client.js | `[data-dsh-responsive-part="session-title-cluster"]` flex 居中 crumbs；`> div` 绝对定位 left:0（headerActions 脱离流） |
| crumb 限宽放开 | client.js | `nav button { max-width: none; white-space: normal; word-break: break-all }` |
| 新会话按钮字色 | navia/patches.css | `[data-pane="sidebar"] [class*="newSession"] { color: #f2e8d5 }`（与 commit hash chip 同款） |

## 插件改动生效链路（重要）

- `dsh-font-serif` 无 src、无构建脚本，`lib/client.js` 就是手写源（`window.__ModuleLoader__.load()` 格式）
- node_modules 里是 pnpm symlink 直连 `packages/dsh-font-serif/`——**改文件即生效，不需要 npm 重装/编译**
- 改完只需：重启 dsh web → Ctrl+F5

# 皮肤卡顿性能排查（2026-08-31 沉淀：navia 输入卡破案实录）

## 铁律：先查 GPU 分配，再动 CSS

**皮肤"输入卡/滚动卡"，第一件事不是改 CSS，是查 Firefox 用的哪张显卡。**

笔记本双显卡（Intel 核显 + NVIDIA 独显）下，Firefox 常被分配到核显渲染——WebRender 合成是 GPU 密集活，核显（共享系统内存）扛不住"背景图 + 多层半透明 + backdrop-filter"的合成管线。**CSS 只能优化"每一帧多重"，GPU 决定"每一帧多快"**——瓶颈在 GPU 时，CSS 优化全是治标。

本场实测：navia 输入卡，做了 webp 缩图（-81%）、毛玻璃 24→8px 降档、半透明全实色三组 CSS 优化，只改善约 1/3；**强制 Firefox 换 RTX4060 后卡顿直接消失**。

## 排查清单

1. **查 GPU**：`about:support` → 图形（Graphics）段 → 看 **GPU #1 的"活动"**：
   - `活动 = 是` 的 GPU 就是 Firefox 实际渲染用的
   - 如果 Intel 是"是"、NVIDIA 是"否"（但 NVIDIA 被检测到、驱动正常）→ 就是 GPU 分配问题
2. **强制独显**（三管齐下）：
   - NVIDIA 控制面板 → 管理 3D 设置 → 程序设置 → 添加 firefox.exe → 首选图形处理器 = 高性能 NVIDIA 处理器（最可靠）
   - Windows 设置 → 系统 → 屏幕 → 显卡 → 添加 Firefox → 高性能
   - `about:config` → `gfx.webrender.force-discrete-gpu` = true
3. **完全重启 Firefox**（任务管理器清干净 firefox.exe 进程，后台残留会让新设置不生效）
4. **验证**：`about:support` GPU #1 活动变 NVIDIA → 再测

## 本场沉淀的经验

| 经验 | 内容 |
|---|---|
| backdrop-filter 是"开关型"成本 | Firefox 合成器里 8px 和 24px 一样卡——调半径空间有限，要么有（卡一点）要么没有（流畅）。降档不如换 GPU 实在 |
| 背景图优化看纹理内存 | JPEG→WebP + 缩分辨率：main.jpg 7491px/104MB 纹理 → webp 3840px/26MB。核显（共享内存）下这步尤其值；但**格式/尺寸不解决输入卡**（解码后都是 RGBA 位图，每帧采样成本一样） |
| 半透明层有成本但小 | 多层嵌套 rgba 背景（scrollport+dialog+chat-flow 叠罗汉）全实色后只快"一些"——有贡献但不是大头 |
| 性能 profile 工具 | Firefox 性能面板导出 profile JSON → `~/deepseek-harness/tools/ff-profile-analyze.py <profile.json>` 解析类别占比（JS/Layout/Paint/Composite）与栈顶热点。注意：录制必须覆盖输入过程（墙钟几秒），录完火焰图要看到紫色/橙色块，全灰=没录到 |
| 本次 navia 定档 | 毛玻璃 composer/header 24→16px（折中）、sidebar 14→6、dialog 12→8；webp 已生效（7389869、bc4edb1） |

## 一句话结论

**皮肤卡 → 先 `about:support` 看 GPU #1 活动状态 → 强制独显 → 再谈 CSS。** 本场三次 CSS 优化加起来不如换 GPU 一下管用。

# Firefox backdrop-filter 包含块劫持（2026-09-02 沉淀：composer 滚出视口破案实录）

## 一句话结论

**backdrop-filter（同 filter / transform / will-change:transform / contain）会使元素成为 fixed/absolute 后代的包含块**——容器内 fixed 浮层（tooltip/menu/picker）的"视口坐标"被静默改写成"相对容器坐标"。容器在滚动区（overflow:auto 容器内）时最致命：浮层坐标变成超大内容偏移 → 撑出 scrollable overflow → 滚动容器 scrollH 虚高 → 能滚过真实内容，内容区被滚出视口。

## 症状（本案）

- 滚到底后 composer 输入区整体跑到视口上方；发送按钮的 tooltip 反而孤零零钉在视口底部
- 随机复现（tooltip 何时挂 DOM 决定何时埋雷——hover 过发送按钮就埋）；滚动、强制 reflow 都修不好（布局树"自洽"，Firefox 认为 scrollH 虚高是正常布局）

## 机制链（现场实证）

1. navia 给 `[class*="composerStack"]` 加 `backdrop-filter: blur(16px)`（毛玻璃）
2. Firefox：backdrop-filter 使 composerStack 成为 fixed 后代包含块（规范行为）
3. 官方发送按钮 tooltip（`position:fixed`，JS 按视口坐标写 inline `top:707.9px`）坐标被重新解释为"相对 composerStack"
4. tooltip 布局位置落在 stack 内 707.9px → stack.scrollH 133→709（虚高 576）
5. overflow:visible 传播 → scrollBody.scrollH 虚高 576 → maxScroll 虚高
6. 用户滚过真实内容 → seat(composer) 滚出视口顶部；tooltip 显示位置 = stack顶(−128)+707.9 ≈ 视口底部 580

关键证据：现场移除 tooltip → stack.scrollH 715→139、scrollBody.scrollH 回落 576、seat drift −0.2 回底粘住。

## 排查手法（可复用）

- **判"布局真错"还是"绘制错位"**：getBoundingClientRect 报出错值 = 布局真错（不是画歪），别再查合成层
- **scrollH 虚高检测**：`scrollBody.scrollHeight` vs 最后子元素 `offsetTop+offsetHeight` 的差 > 0 = 存在 phantom overflow
- **二分定位溢出源**：容器内逐子树 display:none，看 scrollH 何时回落（本案沿 composerStack → composer.bar → YIbhGa_trailing 命中 tooltip，一行一行砍出真凶）
- **强制 reflow 六法全失败本身就是诊断信号**（sticky toggle / overflow toggle / display none / padding jolt / scrollTop reset / resize 事件全无效）→ 说明布局树自洽，别在"刷新布局"上耗时间，去找 phantom overflow 的实体

## 纪律（写入规范）

1. **滚动区（overflow:auto/scroll 容器）内的容器一律禁止 backdrop-filter**（8/29 Firefox 合成 bug + 9/2 包含块劫持，同一族的两张脸）
2. 给任何容器加 backdrop-filter / filter / transform 前先问：容器内有没有 fixed/absolute 浮层（tooltip/menu/picker）？
3. 伪元素（::before / ::after）带 backdrop-filter 是安全的（没有后代可劫持）——毛玻璃效果优先放伪元素
4. 已落实：navia composerStack 去 blur（git dcc4bad）、data-chat-flow 恢复 backdrop-filter:none（aa8b6b9）；conversation-header 非滚动区保留 blur 但注释记录风险与处置指引

## 同族机制提醒

- 受害浮层不止 tooltip：菜单、popover、picker、portal 都可能是 fixed，症状都是"坐标错位 / 撑出滚动"
- 官方 blue-fantasy 皮肤的 composerSeat:before blur(6px) 是伪元素方案（安全，可对照）
- 无关但同场发现：skin-center semantic-adapter 用宽泛选择器 `[data-side]` 给官方 tooltip 误打 `data-dsh-part="resize-handle"` 标记（官方 tooltip 的 data-side 是方向属性）——纯死标记、无皮肤 CSS 消费，无害；若日后要打 resize-handle 应改用更精确的选择器（如 `[data-dsh-frame] [class*="handle"]`）

# 皮肤字体变量 body 克隆劫持（2026-09-06 沉淀：matrix 不吃 dsh-font-serif 破案）

## 一句话结论

**皮肤在 `:root`/`html` 重定义字体变量（`--dsw-font-family`/`--ds-font-family-code`）时，skin-center CSS 管线会把它们 clone 到 `html[data-dsh-skin="<id>"] body` 上——CSS 变量继承在最近祖先定义处停止，body 的克隆劫持整个正文子树，全局字体插件写在 `:root` 的 `!important` 值穿不过 body。** 插件字体对 navia/furina 等"不定义字体变量的皮肤"天然生效；对 matrix（等宽栈）、xp（sans 栈）这类自定义字体栈的皮肤失效。

## 机制链（curl 实测 transform 后 CSS 铁证）

1. `matrix/skin.css` 第 1-3 行在 `:root` 定义 `--dsw-font-family: Menlo/Consolas/…monospace`
2. skin-center host-side 管线（`transformSkinCss`）强制 scoped：`:root` **合并进** `html[data-dsh-skin="matrix"]`，并对裸 root 块做 **root→body 克隆**——实测输出中字体变量同时出现在 `html[data-dsh-skin="matrix"]` 与 `html[data-dsh-skin="matrix"] body` 两个块
3. dsh-font-serif 插件在 `:root { --dsw-font-family: 衬线栈 !important }` ——即使 `!important` 也只决定 **html 元素自身**的计算值
4. body 上的等宽克隆（normal 声明）是 body 子树内**最近的定义** → 组件继承等宽值；html 上的衬线值根本传不到组件
5. navia/furina 不定义字体变量 → 无 body clone → 组件变量解析一路回溯到 html → 吃到插件衬线 ✓

## 修复（已落实，git 6b81bf2 + 9e874c0）

- 位置：**dsh-font-serif/lib/client.js**（不动 matrix/xp 市场本体；与 furina/navia 分割线特判同先例）
- 手法：`html[data-dsh-skin="matrix"], html[data-dsh-skin="matrix"] body, html[data-dsh-skin="xp"], html[data-dsh-skin="xp"] body { --dsw-font-family: … !important; --ds-font-family-code: … !important; }` 双锚点压回（matrix 首案 6b81bf2，xp 同构并入 9e874c0）
- 字体栈值提为 `SERIF_FAMILY`/`CODE_FAMILY` JS 常量（单一权威源，:root 块与特判块共用）
- code/pre 保留 matrix 原版 Menlo（patches.css 组件级直接声明，终端美学——用户决策 2026-09-06）

## 可复用排查手法

- **皮肤不吃全局插件变量** → curl `/api/skin-center/v2/skins/<id>/stylesheet` 看 transform 后输出：字体/颜色变量是否被 clone 到 `… body` 块
- **判变量继承劫持**：body 上有定义 = 子树全被劫持；F12 查组件 computed 值 vs body computed 值即可定位断层在哪一层
- 同族提醒：xp 皮肤同样中招（Tahoma sans 栈）——已并入同一特判块（git 9e874c0）；xp 无组件级 code/pre 硬编码，仅变量压回即可
- 插件 client.js 与 node_modules 是**硬链接**关系（pnpm file: 本地包）——用 edit 类工具改写会写穿硬链接（写时复制），**改完必须重链**：`rm node_modules/dsh-font-serif/lib/client.js && ln packages/.../lib/client.js node_modules/.../`；服务端实时读盘（no-cache），无需重启 dsh web，Ctrl+F5 即生效


# 字体方案收敛到 body 锚点（2026-09-19 沉淀：Deep Current 不吃字体 → 逐皮肤特判改一般化）

## 一句话结论

**"皮肤在 `:root` 重定义字体变量"是一个会反复发生的类，不该逐皮肤特判——把免疫声明落在 body 上（`html body { … !important }`）即可一次性覆盖所有现存与将来皮肤：skin-center 克隆的落点就是 body，而克隆出的字体声明从不带 `!important`，同一元素（body）上层叠先比重要性再比特异性，本块必胜。**

## 触发（第三例）

把字体方案推广到 `deep-current`（深流）。curl 实测确认它同样在裸 `:root` 重定义 `--dsw-font-family: -apple-system, …`（`skin.css:25`），管线 clone 到 `html[data-dsh-skin="deep-current"] body` —— 与 matrix/xp 同构，而旧版四锚点特判不含它 → 字体失效。（deep-current 不定义 `--ds-font-family-code`，代码族本来就生效。）

## 为什么换成 body 锚点，而不是再加两个锚点

1. 克隆的**落点就是 body**：`transformSkinCss` 的 `bodyCloneProperty()` —— token 类（`--dsw-alias-*`/`--dsw-specific-*`）剥掉 `!important`（让 body 上的暗色变体生效），**其余自定义属性原样保留**
2. 三个中招皮肤的克隆字体声明**全部不带 `!important`**（实测 matrix / xp / deep-current 三份 transform 输出）
3. CSS 层叠顺序：来源与重要性 → 层叠层 → 特异性 → 出现顺序。我方 `html body`（0,0,2）带 `!important`，皮肤 `html[data-dsh-skin=x] body`（0,1,2）无 → **重要性先于特异性，我方胜**
4. 于是逐皮肤枚举被一份规则取代；新增市场皮肤（只要不用 `!important` 写字体变量）自动免疫

**退路**：若日后某皮肤故意以 `!important` 写字体变量（今天 9 个皮肤都没有），再补回显式 `html[data-dsh-skin="…"] / html[data-dsh-skin="…"] body` 锚点——即旧版 matrix/xp 的写法。

## 落地（2026-09-19）

- 位置：`dsh-domus/profiles/web/packages/dsh-suigintou-ui-patches/lib/client.js`（现役包名；`:root` 基线块保留）

- **顺带清理**：删除改名残留孤儿目录 `packages/dsh-font-serif/`（不在 package.json dependencies/bundles、node_modules 里没有、内部 `SERIF_FAMILY` 还是旧值）——它是"改了不生效"类事故的温床。已归档 `backups/dsh-font-serif-orphan-20260919-173145.tar.gz`

# 字号基准 + 皮肤字族全局压制（2026-10-07 沉淀：22px→18px 视觉定稿 + matrix code/pre 破案）

## 一句话结论

DSH 的 markdown 字号有**唯一上游** `--dsh-content-font-size`（改一处，标题族等比跟随），
但 **`code` / `code-block` 是硬编码绝对值不参与该链**，必须单独覆盖；
皮肤对 `code/pre` 的**组件级直接声明**（非变量）只能上选择器——而**逐皮肤特判必然漏**，
已改为「裸元素 + 皮肤上下文」两层通用规则。

## 机制链（`gradient-shadow-text.css` 实证）

```
--dsh-content-font-delta      : calc(var(--dsh-content-font-size, 14px) - 14px)
--dsh-content-font-size-secondary : min(calc(<基准> - 1px), max(13px, calc(<基准> - 2px)))
--dsw-font-markdown-base-font-size : var(--dsh-content-font-size, 14px)      ← 正文
--dsw-font-markdown-h1-font-size   : calc(21px + var(--dsh-content-font-delta))  ← 标题全跟随
--dsw-font-markdown-code-font-size : 12px        ← ★ 硬编码
--dsw-font-markdown-code-block-font-size : 11px  ← ★ 硬编码
```

**★ 简写陷阱（本次踩到）**：`--dsw-font-markdown-code-block: 11px/19px var(--ds-font-family-code)`
把字号**字面量内联**在值里，而 `CodeCard` / `DiffBlock` / `SearchBlock` / `TerminalBlock` /
`CodeBlock` **六处**用 `font: var(--dsw-font-markdown-code-block)` **简写**取值。
CSS 变量是静态替换 —— **只改 `-font-size` 子变量不会重算简写变量**，两者必须一起覆盖。

**代码块头部文字更隐蔽**：`CodeCard.module.css` 的 `.language` / `.title` **完全不声明 font-size**，
字号靠继承自祖先那句 `font: var(--dsl-code-block-banner-font)`（11px）。**没有变量可改**，只能上选择器。

## 定稿值

| 项 | 值 | 说明 |
|---|---|---|
| 正文基准 | **18px** | 先按 22px 做，用户视觉测试后自己改成 18 |
| 代码块 / 行内代码 | **16px**（小四） | 与 12px/11px 原值拉开 |
| 代码块头部文字 | **15px** | 与 16px 略错开，页头不与代码正文等重 |
| 代码字族 | `'Fira Code', '仿宋', 'FangSong', serif` | 与 VSCode 对齐；**不再以 monospace 收尾**（Windows 裸 monospace 的 CJK 落宋体） |

## 皮肤压制：两层通用规则（取代逐皮肤特判）

**起因**：`skins/matrix/patches.css:134` 有
`code, pre { font-family: Menlo, Consolas, JetBrains Mono, monospace }` ——
**组件级直接声明非变量**，skin-center 管线 scope 成 `html[data-dsh-skin="matrix"] code`
（特异性 0,1,2，**无 !important**）。

**2026-09-07 的「保留 matrix 原版 Menlo」决策作废**：用户要求**全局覆盖**，
理由是审美（练书法，认为无衬线观感差，仿宋舒服）。

**12 皮肤全扫结论**：
- 有 `code/pre` 直接声明的：**只有 matrix**
- 在 `:root` 重定义字体变量的：**crt-phosphor / deep-current / matrix / xp**（被既有通用 body 锚点覆盖）
- ★ `crt-phosphor` 是 2026-09-07 之后**新增**的皮肤（当时 9 个 → 现 12 个：新增
  blueprint / crt-phosphor / remiel-starlit）⟹ **逐皮肤特判必然漏**

**落地**：
```css
/* ① 裸元素层：无皮肤也生效；!important 压过任何「非 !important」的皮肤声明 */
code, kbd, samp, pre { font-family: <CODE> !important; }
/* ② 皮肤上下文层：借 [data-dsh-skin] 把特异性抬到 (0,1,2)+，
      防将来某皮肤也用 !important 时被反压 */
html[data-dsh-skin] code, html[data-dsh-skin] pre, ... { font-family: <CODE> !important; }
/* ③ 代码块头部文字（无变量可改，只能选择器） */
[data-code-block-banner] [class*="_language_"],
[data-code-block-banner] [class*="_title_"] { font-size: 15px !important; line-height: 22px !important; }
```
**一份规则覆盖现在与将来的所有皮肤**，结束「发现新冲突 → 加特判」的循环。
（③ 的锚点：`data-code-block-banner` 由 `CodeBlock.tsx` 写死，稳定；类名带 CSS Module 哈希，
故用类名**子串**匹配抗漂移。）

## 2026-10-08 字号口径改造 + 随包可变字体（本节同时刷新上面两节的若干数字）

### 一、字号：从「绝对值 + 覆盖基准」改成「倍率 × 基准」

- **病灶**：补丁把 `--dsh-content-font-size` 写成 `18px !important`，压过了 ui-theme 写在 body **内联样式**上的用户设置 —— CSS 级联里 important 声明赢过普通内联，于是设置面板「字号大小」**整块失效**（devtools 里 inline 显示 17px、computed 却是 18px）。
- **改法**：撤销该覆盖，只保留倍率常量（`CODE_RATIO = 16/18` 等 5 个），接管档位一律写成 `calc(var(--sgt-content-size) * 倍率)`。
- **关键约束**：派生变量**只能挂 `html body`，不可并挂 `:root`** —— `:root` 在 `<html>` 上解析，取不到只写在 body 内联的基准值（会掉 14px 兜底），且 `:root` 特异性 (0,1,0) 高于 `html body` (0,0,2)，挂错会**反过来赢**。
- **官方标题族不动**：那条 delta 链是官方自管的加法式；本包只接管官方硬编码绝对值的那几档（code 12px / code-block 11px / banner 11px）。
- 草稿纸：id=1592（研究）、id=1593（落地）。

### 二、随包可变字体（Source Serif 4 Variable）

- **为什么**：字号可调（10–22）要求光学尺寸跟着动。手工分档是**静态映射**，字号一调就失配；可变字体的 `opsz` 轴是动态的 ⇒ 配合已存在的 `font-optical-sizing: auto` 自动选档。
- **全量、不子集化**：本机场景是科幻 + 人类学讨论，数学符号 / 希腊字母 / IPA / 转写变音符都是高发字符。
- **落点（四条路都试过）**：

  | 路 | 结论 |
  |---|---|
  | 内嵌进 client bundle | base64 后 +556 KB，bundle 16 KB → 570 KB |
  | 皮肤 `assets/` | 可达但语义越界，且响应头 `cache-control: no-store`，417 KB **每次加载重传** |
  | `/plugins` 路由 | 只服务 client bundle 与 source map（官方文档：「绝不提供其他字节」） |
  | **✅ host 半区自注册前缀路由** | `ctx.webServer.register({kind:'prefix'})`，缓存头自己掌握 |

- **实现**：`lib/index.js` 注册 `/api/dsh-suigintou-ui-patches/fonts/…`，带 `immutable` 缓存 + 内容哈希 ETag；`lib/client.js` 里 `@font-face` 指向它，并把 `'Source Serif 4 VF'` 放到 `SERIF_FAMILY` 首位（后面保留静态档作降级）。
- **命名纪律**：路由前缀**含完整包名** —— 导出脚本是「字面替换完整包名」，这样发布后自动变 `/api/dsh-sandrone-ui-patches/fonts/…`，脚本零改动。（缩写 `sgt-`、或单独出现的 `suigintou`，都**不在**替换表里。）
- **依赖写法**：host 半区用 `ctx.inject(['webServer'], cb)` **回调**，**不写进顶层 `inject`** —— 服务缺席（headless）时只跳过本半区，不让整个插件加载失败（2026-10-07 模型身份的教训）。写法与 `packages/host/open-in-app` 同源。
- 草稿纸：id=1594。

### 三、navia 皮肤

- **preview 补图**：`skins/navia/preview/navia.jpg`（1600×900 / 183 KB）。⚠️ schema 要求 `preview.light` 与 `preview.dark` **同时存在**，只填一个会让 manifest 校验失败、**整张皮被剔除出 catalog**（全部资源 404，皮肤从列表消失）。现两键同指一个中性文件名。

# 侧栏字族改思源宋体（2026-10-09 沉淀：从「光学尺寸」追到「渲染地板」，再定案左右两栏）

## 一句话结论

**两件事叠在一起，别只记一件：**
1. **Display 与 Text 画风不同，是 `opsz` 光学尺寸** —— Source Serif 4 那五档是**五套分别画的字形**，不是缩放关系；17px 正文配 Display（60pt 档）本来就是误配。
2. **「西文显胖」的元凶是仿宋** —— 它的竖画只有 0.035em，是整条栈里最细的东西（比任何 Source Serif 档细 1.9–2.7 倍）；而侧栏字号是上游**字面 px**，14px 下仿宋**永远画不出一个纯黑像素**。

落地：左右两栏改思源宋体一体，正文与编辑器正文不动。（会话里的「编辑日志」卡最终**没换字族**，只抬了字号 —— 见 §七。）

## 一、光学尺寸：五档是五套字形（实测，非推测）

`SourceSerif4Variable-Roman.otf` 的 `fvar`：**`wght` 200–400–900、`opsz` 8–**20**–60**。随包 woff2 实测**轴没被实例化掉**（19 表 / 1464 字形 / 919 码位），named instances 30 个。

| 档 | opsz | x高/大写(OS/2) | `l` 竖干 | `o` 发丝 | 对比度 | 同串宽 |
|---|---|---|---|---|---|---|
| Caption | 8 | 0.758 | 0.0950em | 0.0600em | 1.58 | 1.14× |
| Small Text | 16 | 0.725 | 0.0900 | 0.0500 | 1.80 | 1.05× |
| **Text** | **20** | 0.709 | 0.0850 | 0.0450 | 1.89 | 1.00× |
| Subhead | 32 | 0.700 | 0.0775 | 0.0375 | 2.07 | 0.97× |
| **Display** | **60** | **0.675** | 0.0675 | **0.0200** | **3.38** | 0.91× |
| — Times New Roman | — | **0.676** | 0.0800 | 0.0325 | 2.46 | — |
| — Georgia | — | 0.695 | 0.0925 | 0.0375 | 2.47 | — |

> **TNR 对账**：x高/大写 0.676 vs Display **0.675** —— 到小数点后两位重合。所以「Display 像 TNR」不是错觉，是**同一个位置上的东西**：TNR 本就是 transitional 高对比正文体。

**出处**：Adobe [Source Serif gets optical sizes](https://blog.adobe.com/en/publish/2021/03/04/source-serif-gets-optical-sizes)（五档、60 个 style、18 个 master；"sturdy, simplified details … morphs into an elegantly swelling high-contrast variant"）；[CSS Fonts 4 §8.1](https://www.w3.org/TR/css-fonts-4/#font-optical-sizing-def)（"strokes are often thicker with larger serifs"）；[FontLab: Optical sizing's lost century](https://blog.fontlab.com/2025/05/27/optical-sizings-lost-century/)（Caslon 1720 每号独立冲模；照排丢了它一百年）。

⚠️ **`auto` 的 px↔pt 换算至今无定论**（[CSSWG issue #13331](https://lists.w3.org/Archives/Public/public-css-archive/2026Jan/0267.html)：实现"simply sets `opsz` to the point size"；FontLab 原文："Physical points? CSS pixels? … 'auto' is doing slightly different things on each platform"）。17px 时落 **12.75–17** 之间，**两端都远离 Display 的 60**。想钉死用 `font-variation-settings: 'opsz' N`（规范第 12 顺位，高于第 9 顺位的 `font-optical-sizing`；只写一个轴不会把 `wght` 打回默认）。

## 三、落地（本次改动）

```css

[data-slot="rightbar"] [class*="editorBody"] { font-family: SERIF_FAMILY !important; }  /* 例外 */
```

- **锚点是官方的**：`[data-slot="<key>"]` 由 `ui-renderer/src/client/scoped-slots.tsx:1088` 渲染，文件原话 —— "**every slot render site exposes a stable `[data-slot="<key>"]` wrapper — the addressable seam dynamic styles target**"，外层 `display:contents`（布局中性）。**比 CSS Module 哈希子串可靠得多**，以后新增 UI 覆盖优先找它。槽名：左栏 `sidebar`（ui-sidebar 注册），会话列表在子槽 `sidebar.workspaces`；右栏 `rightbar`（ui-layout 注册），插件在 `rightbar.session`。

## 六、v2 修正：`font:` 简写漏网 —— 文件浏览器目录树（2026-10-09 当晚）

**症状**：左右两栏都成了，只有右栏的**文件浏览器目录树**还留在仿宋（用户报「小字体重灾区」）。

**排查**：dump 了整个 DOM（`<源码盘> Serif 4 字形差异原因 — DSH 本地构建 文件浏览器目录树.htm`），祖先链是

```
div[data-slot="rightbar"] → aZQLhq_session → div[data-slot="rightbar.session"] → aZQLhq_panel
 → aZQLhq_panelBody → _surface_6nhg2_125 → … → div[data-slot="sidebar.right.pane.tab"]
 → nArs4W_editorTreePanel → nArs4W_explorerBody → nArs4W_explorerRow → span.nArs4W_explorerName
```

—— **确实在 `rightbar` 子树里、也确实不在 `editorBody` 里**。所以不是「没匹配上」，是有东西在中间重新声明了 `font-family`。

**根因（两条叠在一起）**：

1. `dsh-better-sidebar` 大量用 **`font:` 简写 token**：`.nArs4W_explorerRow { font: var(--dsw-font-xxs-12) }`。
2. `--dsw-font-xxs-12` 在 ui-theme 里定义成 `12px/18px var(--dsw-font-family)` —— **字族被烘进了 token**。而 CSS 自定义属性的 Computed value 是「**specified value with variables substituted**」（[css-variables-1](https://www.w3.org/TR/css-variables-1/) 的 `--*` propdef）⇒ 嵌套 `var()` 在**声明处**（`:root` / `html body`）就解析完，之后按**计算值**继承。⇒ 在侧栏根上重定义 `--dsw-font-family` **不会重算**这个 token。
3. 再加上 `font:` 简写把它变成**元素上的直系 `font-family` 声明** —— 继承永远压不过直系声明。两条合起来，树就落回仿宋。

**左栏为什么没事**：`Rows.module.css` / `SidebarRoot.module.css` 里**一个 `font-family` / `font:` 简写都没有**（只有一条 `font: inherit`），纯靠继承 ⇒ v1 的属性层规则就够。**同一个补丁，两栏的生效机制不同**。

**修法（v2）**：用各 token **自己的子变量**（`-font-style` / `-font-weight` / `-font-size` / `-line-height`，它们只是数值与长度、不含嵌套 `var()` ⇒ 继承干净）在侧栏根上**重建**这 27 个字族简写 token。刻意只列字族简写；**代码族一概不碰**（`--ds-font-family-code` / `--dsw-font-mono` / `--dsw-font-markdown-code*`）—— 终端、代码块、git diff 的等宽必须原样。这正是「token 层」相对「`*` 通配层」的好处：只会动原本就用 `--dsw-font-family` 的东西。

编辑器正文例外同样进了 token 重算的选择器（编辑器里 `.editorMd` 也是 `font:` 简写），只是 `--dsw-font-family` 被第三条规则改回原栈。

**纪律（新增，两条都很值钱）**：

- **`font:` 简写是 `font-family` 的隐形「直系声明」**。查「谁覆盖了字体」时只 grep `font-family` 会漏 —— **必须连 `font:` 一起 grep**。这次就是栽在这里。
- **CSS 变量是「声明处解析、按计算值继承」**：`--a: var(--b)` 之后在子孙上改 `--b`，`--a` **不会重算**。要给一棵子树换字族，光改 `--dsw-font-family` 不够 —— 凡是「把字族烘进值里」的 token 都要在**同一个根**上重写。（本包 2026-10-08 那条 `--dsw-font-markdown-code-block` 注释记的是同一个坑的另一面：「只改 `-font-size` 子变量不会重算简写变量」。）
- 重建简写时**用子变量、不要抄字面量**：抄了就和上游脱钩，上游一改尺寸这边就成了魔数。

## 七、第三处：会话里的「编辑日志」卡（2026-10-09 定案：**只抬字号，不动字族**）

1. **字族：刻意不动。** 第一版曾在卡片根上覆盖成思源宋体（变量层 + 属性层各一条，因为 `.path` 直接读 `var(--dsw-font-family)`、`.title`/`.toggle` 走 `.header { font: inherit }` 继承），**已撤**。

   - **对比：左右两栏那两块确实换了字族** —— 理由不是审美，是**侧栏字号被上游布局锁死在 14px、行高只有 32px，抬不动**（抬到 18px 行高得跟着到 ~40px，侧栏密度掉 25%）。**同一件事，两处解法不同，判据是「这个元素抬不抬得动字号」。**
2. **字号**：改成「`--sgt-content-size` × 倍率」，倍率按「**基准 20px 时小字 ≥ 16px**」反推：`title 0.90 / path 0.85 / toggle 0.85 / row 0.80 / stat 0.80` ⇒ @20px = **18 / 17 / 17 / 16 / 16px**。标题留在同一条乘法链上，层级不塌。
